# 21. Анализ пакетов

Страница **«Анализ пакетов»** (меню «Анализ») — разбор сетевой записи по уровням
на сервере отдела, без интернета и без установки программ на рабочие места:
открывается в браузере, как всё рабочее место. Файл может быть любого размера —
гигабайты и десятки гигабайт: он разбирается потоком, а всё, что видно на
странице, растёт по мере разбора (21.6).

## 21.1. Откуда берутся пакеты

- **Файл из браузера**: pcap (микро- и наносекундный, оба порядка байт), pcapng
  (блоки SHB/IDB/EPB/SPB, разрешение времени интерфейса), `.sig`/`.dpo` (кадры с
  двухбайтовой длиной — разметка определяется сама). Файл уходит на сервер
  **кусками** (по 8 МБ, не больше предела тела запроса): над записью видна полоса
  загрузки, **«Отменить загрузку»** останавливает её и удаляет запись. Оборвалась
  связь — кусок повторяется сам (до шести раз с паузой); закрыли окно — на
  странице записи выберите тот же файл и нажмите **«Продолжить»**: загрузка пойдёт
  с того места, где остановилась (сервер сверяет размер, а повтор уже принятого
  куска — по байтам). Разбор начинается **с первого куска**: пакеты, дерево
  протоколов и статистика появляются, пока файл ещё грузится.
- **Файл на сервере — по ссылке** (кнопка **«Файл на сервере…»**): обзор папок
  входных файлов сервера (их задаёт администратор, `input_dirs`, 21.6), с поиском
  по имени во всех подпапках, размером и датой. Файл разбирается **на месте** —
  без загрузки через браузер и без копии: гигабайты начинают разбираться за
  секунды. Если файл после открытия изменили или удалили, страница так и скажет
  («файл … изменён на сервере после открытия — откройте его заново»), а не
  покажет чужие байты; список, дерево и статистика при этом остаются — они
  хранятся у записи.
- **Из разбора потока**: у этапа, после которого получились пакеты IP или
  кадры, — кнопка **«Пакеты»**. Кадры без канального заголовка (после HDLC,
  из .sig) разбираются «по признакам»: IP по контрольной сумме заголовка,
  PPP по `FF 03`, Cisco HDLC, Ethernet по типу, затем канальные протоколы по
  признакам их стандартов — Frame Relay (адрес Q.922 и NLPID, LMI), LAPD
  (EA, SAPI 0/1/16/62/63, кадры I/S/U Q.921), LAPB без байта направления
  (адрес A/B/C/D, пакет X.25), AX.25 (позывные), MTP2 (LI сходится с длиной).
  Если разбор потока опознал канальный протокол по всей массе кадров, этап
  выгружается pcap с типом канала (MTP2 — 140, LAPD — 203, Frame Relay — 107,
  AX.25 — 3) и открывается сразу нужным разборщиком.
- **Приём с сети** (пункт меню «Приём с сети»): сервер сам принимает трафик со
  своей сетевой карты или датаграммы на порт UDP; **анализ пакетов вживую** идёт
  следом за приёмом — часами, без предела (21.7).

Записи хранятся (последние 30 законченных) и видны только тому, кто их открыл;
в резервную копию они не идут — пересчитываются из файла.

## 21.2. Что видно

- **Список пакетов**: номер, время от начала, источник, получатель, протокол,
  длина, сведения. Строка окрашена по семейству протокола (TCP, UDP, DNS,
  HTTP, TLS, ARP, ICMP, маршрутизация); ошибки — красным со знаком ⚠. Цвет
  дублирует столбец «Протокол» — он не единственный признак. ↑/↓ — по списку.
- **Дерево полей** — слева, с самого верха: уровни снизу вверх, у каждого
  поля — значение и место в байтах `[34…35]`. Всё прочее о пакете — справа
  от дерева: заголовок с действиями («Следовать за потоком», «Разбирать порт
  как…», «Спросить помощника о пакете»), ошибки, вид байт и дамп. Щелчок по
  полю подсвечивает его байты в дампе; наведение на байт дампа подсвечивает
  поле, из которого он прочитан. Над дампом — готовое выражение фильтра для
  выбранного поля: **«Отобрать такие»**, **«Кроме таких»**.
- **Описание — справа.** Пояснения к разделу и вкладкам (матрица байт,
  протоколы, неизвестные форматы) — в правой панели «Описание», свёрнутой по
  умолчанию; открывается щелчком по ручке у правого края.
- **Дамп байт**: HEX, DEC, BIN или ТЕКСТ (CP1251 для кириллицы), порядок бит
  в байте — старший или младший первым.
- **Контрольные суммы** пересчитываются: IPv4 (заголовок), TCP/UDP (с
  псевдозаголовком IPv4/IPv6), ICMP, ICMPv6, SCTP (CRC32c). Неверная —
  красным и в списке ошибок. У TCP «не сошлась» бывает и у исправного пакета:
  захват на передающем узле до подсчёта суммы сетевой картой — так и написано.
- **Фрагменты IPv4 собираются**: к последнему фрагменту добавлен разбор
  собранного пакета и его собственный дамп.

## 21.3. Фильтр

Язык в духе Wireshark, но свой и безопасный:

| Выражение | Что отбирает |
|---|---|
| `tcp`, `dns`, `arp`, `ip`, `vlan` | пакеты с этим уровнем |
| `ip.addr == 10.0.0.0/8` | адрес (любой из двух) в подсети |
| `ip.src == 10.1.1.1`, `ipv6.dst == 2001:db8::1` | источник, получатель |
| `tcp.port == 443 or udp.port == 53` | порты |
| `port in {53 123 161}` | порт TCP, UDP или SCTP из списка |
| `dns.qry.name contains "mail"` | подстрока без учёта регистра |
| `http.host matches "^mail\."` | регулярное выражение |
| `frame.len > 1000 and not arp` | длина, логика `and`/`or`/`not`, скобки |
| `http.request.method == "POST"` | любое поле из дерева (ключ — в подсказке поля) |
| `frame[12:2] == 0800` | байты 12–13 кадра (HEX: `0800`, `08:00`, `0x0800`; десятичное — `2048`) |
| `payload[0].hi == 0xA`, `payload[0].lo == 5` | полубайты первого байта нагрузки верхнего уровня |
| `frame contains ff:d8:ff`, `payload contains "JFIF"` | последовательность байт или текст |
| `expert` (или `ошибки`) | пакеты с ошибками (суммы, обрывы) |
| `данные` (или `data`) | нагрузка, которую ни один разборщик не взял |

Статистика на всех вкладках считается по отобранным пакетам.

Ошибка в выражении видна по мере набора — поле краснеет, под ним сказано,
что не так, ещё до «Отобрать». Применённые фильтры запоминаются в этом
браузере (последние 20) и предлагаются при наборе. Клавиши: **/** — к
фильтру, **Esc** — вернуть применённый; в списке пакетов **↑/↓**,
**PageUp/PageDown** (по 20), **Home/End**.

## 21.3а. Разбирать как

Служба на нестандартном порту (HTTP на 8888, DNS на 5000, свой SIP) по
таблице портов не узнаётся. Кнопка **«Разбирать как…»** в шапке захвата
или **«Разбирать порт N как…»** у пакета задаёт правило «UDP/TCP порт →
разборщик»; запись разбирается заново в фоне, фильтры и статистика видят
новый разбор. Разборщик и по выбору аналитика проверяет, что данные его: не
подошли — это видно в ошибках пакета («разбирать как BGP (порт 8888): данные
не подошли»), и разбор идёт дальше обычным путём. «Не разбирать (данные)» —
когда угадывание по содержимому ошибается. Правило снимается крестиком.

## 21.4. Вкладки

- **Обзор** — главное одним взглядом, считается само: пакеты, объём,
  длительность, средняя скорость, пакеты с ошибками, объекты и файлы (плитка
  и карточка «сколько каких видов»);
  протоколы с долями, главные диалоги IP, имена DNS, серверы TLS (SNI), узлы
  HTTP, виды ошибок, неразобранная нагрузка по портам. Блок **«На что
  посмотреть»** — приметы с кнопкой отбора: протоколы открытым текстом (HTTP,
  FTP, Telnet, POP3, IMAP, SMTP, SNMP, TFTP, Syslog), DNS-запросы без ответа
  (сопоставление по идентификатору и порту клиента), суммы TCP, не сошедшиеся
  у большинства пакетов (захват на передающем узле, а не порча), больше всего
  неразобранного, найденные файлы. Любая строка обзора — щелчок: отбор пакетов
  или переход на нужную вкладку.
- **Протоколы** — иерархия протоколов: сверху схема-«сосулька» (ширина — доля
  пакетов или байт внутри узла, ряд — уровень вложенности; двойной щелчок —
  приблизить узел, «хлебные крошки» — назад), ниже дерево-таблица со всеми
  столбцами Wireshark «Protocol Hierarchy» (% пакетов, пакеты, % байт, байты,
  бит/с, % от родителя, кончаются здесь — пакеты и байты), сортировкой по любому
  столбцу, порогом «скрыть мельче N %», поиском, выгрузкой в CSV и JSON (раскрытие,
  клавиши ↑ ↓ ← → и Enter) и карточка узла: доли детей сегментной полосой,
  направления по адресам, диалоги и узлы, первый и последний пакет, выходные
  данные узла (объекты, pcap, поля, потоки — см. 21.4а); кнопки «Показать
  пакеты», «Исключить», «И к фильтру», «Приблизить на схеме». Цвет — уровень
  протокола (канальный, сетевой, транспортный, прикладной), рядом всегда подпись.
- **Диалоги** — Ethernet, IP, TCP, UDP: пакеты и байты в каждую сторону,
  начало, длительность, протоколы; щелчок — отбор пакетов диалога.
- **Узлы** — адреса: отправлено, получено, службы (порты < 1024).
- **Матрица байт** — пакеты строками, байты столбцами, выравнивание от начала
  кадра или от нагрузки верхнего уровня, окно по 16–256 столбцов. Над
  столбцами — **профиль энтропии**: низкие столбики — постоянные поля, типы,
  синхрослова; высокие — данные. Щелчок по заголовку — **статистика столбца**
  (или поля 2–8 байт): значения по частоте (щелчок — отбор), энтропия,
  различных значений, полубайты, доля единиц по битам и вывод: «постоянное
  поле», «счётчик +1», «растёт с шагом», «поле длины: длина пакета − k»,
  «поле типа», «похоже на случайные данные». **Правая кнопка** на ячейке —
  отбор по байту, полубайту, полю, «кроме», статистика; на заголовке —
  статистика, начать матрицу с этого байта. Вид — HEX/DEC/BIN/ТЕКСТ, порядок бит.
- **Время** — пакеты или байты за интервал (одна величина за раз), с таблицей.
- **DNS** — запросы и ответы: клиент, сервер, имя, тип, ответы, код.
- **HTTP** — запросы с ответами: метод, узел, адрес, код, агент.
- **TLS** — ClientHello: имя сервера (SNI), ALPN, версии.
- **Объекты и файлы** — всё, что передано: тела HTTP и части форм, файлы FTP
  и TFTP, письма и вложения, звук и видео RTP, сообщения WebSocket, JSON,
  файлы по сигнатуре в неразобранных потоках; вид по содержимому, опись
  архивов, скачивание по одному и ZIP с описью (подробно — 21.4а).
- **Ошибки** — по видам, с номерами пакетов.
- **Неизвестные форматы** — нагрузка без известного разборщика по группам
  (транспорт и порт службы): поля неизвестного формата (постоянные, счётчики,
  длины, типы) и CRC вслепую — тот же анализ, что у кадров потока.

**Следовать за потоком** (у пакета TCP/UDP/SCTP): нагрузки в обе стороны по
порядку, у TCP — по номерам последовательности, повторы и перекрытия
отбрасываются; текстом или HEX; кнопка отбирает пакеты потока.

**Выгрузка**: отбор — в pcap, pcapng, CSV или JSON; «Выходные данные» — всё
сразу одним ZIP с описью (21.4а).
**Спросить помощника** — о захвате (иерархия, диалоги, ошибки) или о пакете
(всё дерево полей с местами в байтах): помощник объясняет по RFC и стандартам
из библиотеки.

## 21.4а. Объекты и файлы: что выдаётся в файлы

Вкладка **«Объекты и файлы»** выдаёт всё, что передано в захвате, — как «Экспорт объектов» в
Wireshark, только шире: не одни тела HTTP, а файлы FTP и TFTP, письма с вложениями, звук и видео
RTP, сообщения WebSocket, значения JSON и файлы, найденные по сигнатуре в том, что протоколы не
разобрали. Объекты строятся из пакетов под текущим фильтром отбора. У каждого объекта есть вид, имя,
тип, длина, поток, пакеты, заметки и сами байты. Имя берётся из Content-Disposition, адреса, команды
FTP, имени TFTP или вложения; если его нет, имя составное — из потока и места. Заметки говорят о
снятом сжатии, обрыве, пропусках и дырах в потоке.

Таблица на вкладке:

- фильтр по виду;
- щелчок по строке переводит к первому пакету объекта;
- у каждой строки есть кнопка «Скачать»;
- есть кнопки «Скачать всё (ZIP)» и «Скачать отобранные виды (ZIP)».

Звук RTP слушается прямо в строке (`<audio>`). JSON показывается с отступами. Для ZIP и tar
(в том числе tar в gzip, bzip2 и xz) в раскрывающейся строке показывается опись членов, и любой член
можно скачать отдельно. RAR и 7z только опознаются, без описи. Колонка «Содержимое» показывает вид
по магии и структуре, а не по имени и Content-Type. Например, `.bin` с документом Word внутри будет
показан как «OLE2 (doc)». В обзоре есть плитка «Объекты и файлы» и карточка с числом объектов каждого вида.

Все таблицы и константы взяты из документов, с номерами разделов в комментариях кода

**ZIP объектов.** Имена в архиве уникальны: одинаковые получают «-2», «-3». «..», «/» и
управляющие символы заменяются, так что выйти из архива нельзя. Рядом лежит `опись.csv` со
столбцами: номер, вид, имя, «в архиве», тип, содержимое, длина, поток, пакеты, время, SHA-256, заметки.
В колонке «содержимое» стоит вид файла по содержимому.

**Выходные данные** — кнопка на странице и пункт обзора. Флажками отмечается, что выгрузить:

- отобранные пакеты в pcap и pcapng (SHB, IDB на каждый вид канала, EPB с микросекундами);
- список пакетов в CSV и JSON;
- полный разбор в JSON (дерево полей каждого уровня);
- поля по каждому протоколу в CSV;
- статистику в CSV и JSON: иерархия с долями, диалоги Ethernet, IP, TCP и UDP, узлы, время, DNS,
  HTTP, TLS, ошибки, неизвестные форматы;
- объекты по видам, звук и видео RTP, сырые потоки TCP и UDP по направлениям (`.bin`);
- отчёт-обзор в HTML (без внешних ресурсов, со светлой и тёмной темой) и текстом.

Рядом с каждым пунктом показано, сколько в нём будет. «Выгрузить отмеченное» собирает один ZIP с
папками `пакеты/`, `поля/`, `статистика/`, `объекты/<вид>/`, `rtp/`, `потоки/` и `отчёт/`, а также
`опись.csv` и `опись.json`. В описи для каждого файла указаны путь в архиве, что это, откуда (поток,
пакеты, протокол), время, размер и SHA-256. Что не вошло по пределу объёма, записывается в
`заметки.txt`. ZIP собирается во временном файле, поэтому большие выгрузки не держатся в памяти.

**Настройка выдачи** — кнопка «Настройка». Сервер настроек не хранит: всё запоминается у
пользователя в браузере и уходит параметрами запроса.

| Настройка | Параметр API | Значения |
|---|---|---|
| что отмечено по умолчанию | — | пункты «Выходных данных» |
| имена файлов | `names` | протокол (`0007-архив.zip`), поток и время (`0007-TCP_10.0.0.2_50000_…-20250929T130000-архив.zip`), только номер (`объект-0007.zip`) |
| снимать сжатие HTTP | `decompress` | да / нет (тело остаётся gzip) |
| тишина в пропусках RTP | `silence` | да / нет |
| звук | `audio` | WAV / сырые отсчёты кодека |
| видео | `video` | Annex B / NAL с 4-байтной длиной |
| JSON | `json` | с отступами / сжато |
| пределы | `maxobj`, `maxzip`, `maxcount` | МБ на объект, МБ на выгрузку, число объектов |
| порог дерева протоколов | — | скрыть узлы мельче N % (по умолчанию 0) |
| часовой пояс | `tz` | браузера, UTC или ±ЧЧ:ММ (минуты к UTC) — для времени в описи и отчёте |

**Дерево протоколов** (вкладка «Протоколы») показывает для каждого узла:

- % пакетов, пакеты, % байт, байты, бит/с (байты × 8 / длительность захвата);
- % от родителя по пакетам и байтам;
- сколько пакетов и байт кончаются на этом узле.

В каждой строке есть полоса доли. Сортировка возможна по любому столбцу. Поле «скрыть мельче N %»
прячет узлы, у которых и доля пакетов, и доля байт меньше порога. Поиск сохранён. Дерево
выгружается в CSV и JSON. Доли считаются так же, как Wireshark «Protocol Hierarchy»: от всех
пакетов и байт захвата под фильтром.

Карточка узла показывает:

- доли детей сегментной полосой (плюс «кончаются здесь») по пакетам и по байтам;
- соотношение направлений по парам адресов (А → Б и Б → А), число диалогов и узлов;
- первый и последний пакет;
- выходные данные узла: объекты этого протокола со скачиванием, пакеты узла в pcap и pcapng, поля
  в CSV и JSON, а у протоколов поверх TCP или UDP ещё и сырые потоки `.bin`.

API (права те же, что у соседних запросов страницы: только владелец захвата, чужой захват — 404, без входа — 401):

| Запрос | Что |
|---|---|
| `GET /api/pakety/{ид}/objects?filter=&kind=&path=` | список объектов, виды, отброшенное |
| `GET /api/pakety/{ид}/object/{n}?member=` | объект или член его архива; `Content-Disposition` с `filename*=UTF-8''` и запасным ASCII-именем |
| `GET /api/pakety/{ид}/objects.zip?filter=&kind=&path=` | ZIP объектов с описью |
| `GET /api/pakety/{ид}/export?format=pcap\|pcapng\|csv\|json\|dissect&path=` | пакеты и разбор |
| `GET /api/pakety/{ид}/fields?path=&format=csv\|json` | поля протокола |
| `GET /api/pakety/{ид}/streams.zip?path=` | сырые потоки |
| `GET /api/pakety/{ид}/stats?kind=protocol&path=` | соотношения узла |
| `GET /api/pakety/{ид}/stats-file?kind=&format=` | таблица статистики файлом |
| `GET /api/pakety/{ид}/report?format=html\|txt` | отчёт |
| `GET /api/pakety/{ид}/outputs`, `GET /api/pakety/{ид}/bundle.zip?items=` | пункты «Выходных данных» и общий ZIP |

Все запросы принимают `filter` и параметры настройки выдачи.

## 21.5а. Мутационная проверка

Каждый разборщик проверяется мутантами: в теле функций по одному меняются числа (±1), сравнения,
«и/или», «не», знаки, сдвиги, битовые операции и логические константы, и набор тестов должен
каждого такого мутанта «убить». Тесты сверяют не только итог, но и **раскладку полей** — ключ,
место, длину и сырое значение, выписанные вручную по стандарту, — и отказы разборщиков: чужие
данные дают «нет» без исключения и без уровней. Где мутант пережил тесты, добавлен тест или
упрощён код (лишняя проверка, которую перекрывает следующая, убрана — тогда и мутант пропадает).
Проверки вида «find() ≥ 0», где ноль невозможен по построению, и «split(…, 1)», где берётся лишь
первая часть, заменены на `index` с исключением и `partition` — у них нет неотличимых мутантов.
Мутационная проверка сама нашла ошибки: продолжение N-PDU в SNDCP падало, c= потока SDP
приписывался чужому потоку, оборванная личность в сводке GSM печаталась обрывком; у Reject
ANSI TCAP не требовались обязательные по ASN.1 идентификатор и параметр; многооктетные теги BER
(X.690 8.1.2.4) отвергались, хотя в параметрах MAP неопределённой длины они встречаются; признак
ESM под нулевым шифром читал байт за концом NAS-PDU; у MTP3 и SCCP тесты не сверяли места полей.

Объекты и файлы (`setevoy/obekty.py`, тесты `test_setevoy_obekty.py` и `test_setevoy_obekty_detali.py`),
база сигнатур (`potok/poisk.py`, `test_setevoy_signatury.py`), выгрузки (`setevoy/vygruzka.py`, новые части
`statistika.py`, `zahvaty.py` и запросов API — `test_setevoy_vygruzka.py`) и чистые функции страницы
(настройка выдачи, столбцы дерева — те же тесты в node) проверены так же. Мутационная проверка нашла:
текст длиннее 64 КиБ по-русски признавался «двоичными данными» (граница окна резала букву UTF-8);
у IFD TIFF и каталога OLE стояли произвольные пределы цепочки (256 и 4096) вместо защиты от петель;
имя в каталоге OLE читалось до конца поля, а не по длине; в `_mpa_кадры` проверка «длина < 4»
была недостижима. Проверки, у которых второй вариант неотличим (граница перед более строгой
проверкой, поиск «≥ 0», где ноль невозможен), переписаны без них: `index` с исключением, `partition`,
поиск, возвращающий None, стороны потока «целиком» по умолчанию.

Оставлены только **эквивалентные** мутанты — те, что не меняют поведения ни на каких данных:

| Где | Мутант | Почему эквивалентен |
|---|---|---|
| SSH: правдоподобие пакета | граница 35000 ± 1, «4 + длина» → «3 + длина», «(4 + длина) % 8» → «(4 − длина) % 8» | пакет вместе с полем длины кратен 8 (RFC 4253, 6): соседние с 35000 значения не кратны 8 и отвергаются этой же проверкой; кратность 8 у x и −x одна |
| SSH: отпечаток HASSH | `usedforsecurity=False` → `True` | флаг лишь разрешает MD5 в режиме FIPS, значение хеша то же |
| CFM (MPLS G-ACh) | проверка `тип in ДОП_ETHERTYPE` | для каналов G-ACh регистрирован только CFM; без проверки тот же путь |
| Jmirror | граница заголовка ± 1 | при нехватке данных разбор бросает исключение и откатывается — видимый итог тот же |
| DTAP: наименьшая длина | «< 5» → «< 4» | L3 из одного октета отвергает gsm.dtap по той же границе |
| RTP по SDP, UDPTL | «< 12» → «< 11», «< 4» → «< 3» | короче заголовка RTP (≥ 12 байт) и UDPTL с IFP ≥ 1 байта отвергает проверка длины заголовка и IFP |
| OSI: CLNP | «конец − м < 10» → «< 11», «≤ 10» | PDU из 10 октетов не вмещает длины адреса источника и отвергается проверкой адресов при любой границе |

| Хуки ПЕРЕД_ПОРТАМИ | мутанты, превращающие отказ в чтение за концом | исключение в хуке откатывает уровни — итог тот же; такие места проверяются прямым вызовом разборщика |

| Сигнатуры: обход tar, RAR 4, RAR 5 | «место − начало < ФАЙЛ_ДО» → «≤» | лишний проход на самой границе даёт длину больше предела — `_итог` и так вернёт 0; все прочие выходы в этом проходе — тоже 0 |
| Сигнатуры: длина кадра MPEG-аудио | 12000 → 12001, 144000 → 144001 | полным перебором версий, слоёв, скоростей и частот ISO 11172-3/13818-3: прибавка «скорость / частота» не переходит к следующему целому — длина та же (143999 отличим и убит) |
| Сигнатуры: TIFF, число записей IFD | «м + ifd + 2 > длины» → «+ 3», «≥» | если данные кончаются сразу за числом записей, следующая проверка (IFD целиком) всё равно даёт 0 |
| Сигнатуры: FLV, смещение данных | «< 9» → «< 8» | при смещении 8 «PreviousTagSize0» читается с самого байта смещения (0x08) — не ноль, отказ и так |
| Сигнатуры: Annex B, начало поиска следующего кода | м + 5 → м + 4 | байт м + 4 — заголовок NAL, проверенный на тип (не ноль): код начала с него начаться не может |
| Сигнатуры: Annex B, вложенная проверка | аннотация `int \| None` → `int & None` | аннотации не вычисляются |
| Сигнатуры: PDF, следующий «%PDF-» | начало поиска м + 5 → м + 4, м + 6 | байты м + 4 и м + 5 — «-» и цифра версии: подпись там начаться не может |
| Поиск в битах | сдвиги range(8) → range(9) | сдвиг 8 — тот же поток на байт дальше: находки совпадают по биту с находками сдвига 0 и отбрасываются как повторы |
| Объекты: аннотации полей и подписей | `X \| None` → `X & None` | при `from __future__ import annotations` аннотации (и у dataclass) не вычисляются |
| Объекты: номер объекта по умолчанию | 0 → 1 | номер присваивается всем объектам в `собрать` раньше любого чтения |
| Объекты: `zip(…, strict=…)` | False ↔ True | длины совпадают по построению (сводки и нагрузки, номера и пакеты, блоки и места) |
| Сборка TCP: знаковая разность номеров | внутреннее «+ 2³¹» → «− 2³¹»; внешнее «− 2³¹» → «+ 2³¹», «− 2³⁰», «− 2³²», «− 0» | «± 2³¹» внутри совпадают по модулю 2³²; внешнее вычитание — общий сдвиг всех отметок: порядок и разности те же (внутренний порог 2³⁰ отличим и убит тестом сегмента на 1,5 ГиБ позади) |
| Сборка TCP: пропуски по умолчанию | `заметки(начало=0)` → 1 | пропуск на месте 0 невозможен: первый кусок — опора |
| WebSocket: ключ маски | повторов ключа `n // 4 + 1` → `n * 4 + 1`, `n // 3 + 1`, `n // 4 + 2` | лишние повторы отрезаются срезом по длине данных |
| FTP: передача без объявленного канала | номер пакета объявления 0 → 1 | у такой передачи нет порта — она не сопоставляется, номер не читается |
| FTP, POP3: сравнение номеров пакетов разных сторон | «первый < объявлен» → «≤», «первый пакет сервера < первой команды» → «≤» | пакет принадлежит одной стороне: номера пакетов разных соединений и сторон не совпадают |
| SMTP, POP3: границы письма | поиск «CRLF.CRLF» с «− 2» → «− 3»; конец письма «+ 2» → «+ 3»; дальше «+ 5» → «+ 4» | байт перед CRLF строки DATA или «+OK» — буква, конец там не начнётся; лишняя точка строки конца снимается прозрачностью (RFC 5321, 4.5.2); следующая строка — пустая и пропускается |
| TFTP: имя запроса и окно | `данные[2:]` → `[1:]`; «номер < н» → «≤», «н < следующий» → «≤» | байт кода операции (0x01/0x02) — управляющий знак, `имя_файла` его убирает; на границах окна — сами запросы (код 1/2), а не DATA |
| TFTP, RTP: развёртка номеров | «+ модуль/2» → «− модуль/2» внутри взятия по модулю | разность — ровно модуль, остаток тот же |
| RTP: заголовок короче 12 байт | «< 12» → «< 11» | 11 байт без CSRC отсекает следующая проверка «начало нагрузки > конца» |
| RTP: G.711 без пропуска | «отсчётов < места» → «≤» | при равенстве вставляется ноль отсчётов тишины |
| RTP: преобладающий тип | `most_common(1)` → `most_common(2)` | берётся первый из списка — тот же |
| AMR с экономией полосы | «место + 6 > всего» → «+ 5»; неизвестный тип «−1» → «−2» | 4 + 6k и 8m чётны — разность 5 невозможна; любое отрицательное — отказ |
| Порядок объектов | ключ `пакеты[:1]` → `[:2]` | при равном первом пакете у объектов одного потока следующий тоже по порядку потока — сортировка (устойчивая) даёт тот же порядок |
| ZIP объектов | `compresslevel` 1 → 2 | меняется только степень сжатия, содержимое членов то же |

## 21.6. Файлы любого размера: разбор потоком, память постоянна

**Что видит человек.** Открыл файл — через пару секунд на экране первые
пакеты. Над записью — полоса и строка хода: «разобрано пакетов: 1 234 567 ·
512 МБ из 1,0 ГБ (50 %) · 3 100 пакетов/с · 1,2 МБ/с · осталось ≈ 2 мин 40 с»,
кнопки **«Пауза»**/**«Продолжить»** и **«Стоп»** (разобранное до стопа остаётся
и смотрится как обычно). Раз в секунду страница спрашивает сервер о ходе и
дорисовывает открытую вкладку: в **дереве протоколов** появляются новые узлы,
числа и доли растут; **обзор, диалоги, узлы, ошибки, DNS/HTTP/TLS, время,
неизвестные форматы** — тоже (над ними строка «Разбор идёт — числа растут…»).
**Список пакетов** — виртуальный: в браузере только видимые строки, прокрутка
идёт по миллионам строк (длиннее 8 млн пикселей полоса прокрутки сжимается —
её положение означает долю пути); галочка **«следить за концом»** держит на
экране новые пакеты. Справа от списка — разбор выбранного пакета (на узком
экране — под ним). **Фильтр** работает по уже разобранному и дополняется по мере
разбора: «отобрано 10 664 из 41 436 · проверено 41 436 · растёт». Тяжёлые
вкладки — **«Матрица байт»** и **«Объекты и файлы»** (сборка потоков) — вживую не
перерисовываются: появляется кнопка «Разобрано больше — обновить». Выгрузки
(pcap, pcapng, CSV, JSON) идут потоком — по разобранному к этому мигу.

**Переход между записями и вкладками — мгновенный.** Страница помнит у каждой
открытой записи вкладку, фильтр, выбранный пакет, раскрытое дерево, место
прокрутки списка и последние данные вкладок (12 последних записей в памяти окна;
вкладка, фильтр и пакет — ещё и в sessionStorage): вернулись — всё на месте
сразу, а свежие числа дорисовываются следом. На сервере ничего не пересчитывается:
статистика копится по ходу разбора и лежит на диске.

**Как устроено.**

- **Чтение по записи** (`chtenie.ЧтецЗахвата`): pcap и pcapng — по записи
  (`zahvat_seti/chtec`), файл может ещё дописываться (загрузка кусками): нет целой
  записи — «подождать», а не конец; .sig/.dpo до 64 МБ проверяется целиком, как
  прежде (разметка годна, только если файл проходится ровно до конца), больше —
  разметка выбирается по первым 4 МБ и проверяется по ходу. Оборванный хвост,
  испорченная запись — заметкой, разобранное до них остаётся.
- **Хранилище на диске** (`hranilishe`): индекс по пакету (48 байт: где байты
  пакета, канал, где сводка и поля), сводки для списка и поля для фильтров —
  блоками по 256 пакетов (pickle, сжатый zlib), столбцы времени, длины и
  отпечатка потока. Байты пакетов не копируются — индекс указывает в исходный
  файл (у приёма с сети — копия в `пакеты.bin`, части записи кольцо удаляет).
  Запись индекса пишется последней — страница видит пакет целиком или не видит.
  На диске сверх исходного файла — около 0,3 от него.
- **Статистика по ходу** (`nakopitel`): дерево с «кончаются здесь», диалоги
  Ethernet/IP/TCP/UDP, узлы, ошибки, DNS/HTTP/TLS, обзор и приметы, соотношения
  каждого узла дерева (направления, диалоги, узлы, первый и последний пакет),
  группы неизвестной нагрузки. Итог — тот же, что у расчёта над всеми пакетами
  сразу (это сверяют тесты), пока таблицы не упираются в потолки: диалогов (на
  уровень) и узлов — 50 000, строк DNS/HTTP/TLS — 20 000, узлов дерева — 5 000. Сверх
  потолка новые ключи не заводятся (числа пакетов и байт остаются точными), а
  страница и выгрузка знают об этом («неполно»). Разделы пишутся на диск раз в
  секунду (крупные — реже: запись не отнимает больше ~10 % разбора).
- **Отбор по фильтру** — своей работой следом за разбором: номера отобранных
  (4 байта на пакет) и такая же статистика по ним; восемь последних фильтров
  записи помнятся, три идут следом за живым разбором.
- **Что требует байт** — читается с диска по номерам отбора: матрица (профиль
  столбцов — по первым 100 000 пакетам отбора), столбец (200 000), файлы в
  потоках (1 млн), объекты и сырые потоки (первые 300 000 пакетов, пока их
  нагрузка не больше 64 МБ — сборка держит потоки в памяти сервера); ответ
  говорит, по скольким пакетам собрано. В карточке узла дерева объекты
  собираются по кнопке «Объекты этого протокола…», а не на каждый щелчок. «Следовать за потоком» находит пакеты потока по столбцу
  отпечатков, не читая сводок. Обзор ищет файлы в потоках сам, когда разбор
  кончился и в отборе не больше 50 000 пакетов (иначе — вкладка «Объекты»).

**Параллельно и честно.** Разбор и отборы идут **отдельными процессами**
(`python -m reportgen.setevoy.fon …`) с **пониженным приоритетом ОС** (Windows —
«ниже среднего», прочие — nice 10): разбор пакета на Python — сотни
микросекунд, и в процессе сервера он отнимал бы время у страниц всех людей, а с
обычным приоритетом — ядра у страниц. Сколько работ сразу — вдвое больше ядер
(`pakety_workers`, до 16; отборов — `pakety_filter_workers`, по ядрам, до 8):
каждый сразу видит свой разбор, ядра делятся между людьми поровну; сверх —
очередь, и строка хода показывает место в ней. Из очереди первым берётся работа
того, у кого сейчас меньше идущих, а при равенстве — того, кого обслуживали
давнее: десять файлов одного человека не задерживают остальных. Работа, которая
ждёт данных (файл ещё грузится, приём молчит) или стоит на паузе, места не
занимает. Маленькие файлы (меньше `pakety_process_from_mb`, 8 МБ) разбираются
потоком в сервере — процесс дольше запускать. Сервер перезапустили посреди
разбора — после запуска разбор файла начнётся заново сам.

**Пределы.** Размер файла не ограничен ничем, кроме места на диске:
`pakety_max_mb` (0 — без предела) и запас `capture_disk_reserve_mb` проверяются
**до** отправки — «мало места» человек видит сразу, а не на 49 % загрузки. Один
файл разбирается одним процессом (разбор пакета зависит от прежних: сборка
фрагментов, шаблоны NetFlow, потоки из SDP), поэтому скорость одного файла —
скорость разборщика: 2–4 тысячи пакетов в секунду на ядро. Разные файлы — на
разных ядрах.

**Настройки** (`settings.json`):

| Ключ | По умолчанию | Что |
|---|---|---|
| `pakety_workers` | 0 (2 × ядер, до 16) | сколько разборов идёт сразу |
| `pakety_filter_workers` | 0 (по ядрам, до 8) | сколько отборов по фильтру сразу |
| `pakety_worker_process` | true | работы — процессами (false — потоками в сервере) |
| `pakety_process_from_mb` | 8 | файл меньше — разбирается потоком в сервере |
| `pakety_max_mb` | 0 | наибольший файл, МБ (0 — без предела) |
| `input_dirs` | [] → `<data_dir>/vhod` | папки входных файлов («Файл на сервере…»): путь или `{"имя", "путь", "роль"}`; сетевая папка Windows — `"\\\\сервер\\share"` |

**Файлы по ссылке — безопасность.** Путь внутри папки задаётся относительным;
абсолютные пути, «..», имена дисков отвергаются, а итог после разрешения
символьных ссылок обязан лежать внутри папки: ссылка наружу не видна в обзоре и
не открывается. Папку с `"роль": "head"` видят начальник отдела и выше; чужие
папки для человека не существуют (тот же ответ, что у несуществующей). Модуль
общий (`reportgen/fayly_ssylki.py`, маршруты `GET /api/files/roots`,
`GET /api/files/list?root=&path=&q=`): им же пользуется разбор потоков.

**Замеры** — см. 21.6а.

## 21.7. Приём с сети

Страница **«Приём с сети»** (`#/zahvat`; пункт меню «Анализ → Приём с сети»,
кнопки на «Анализе пакетов» и в «Сессиях потоков»). Одна страница, два режима:
**приём UDP** (адрес и порты — таблица карт ему не нужна) и **приём с сетевой
карты** (таблица карт сервера — только в этом режиме); **«Старт»** — сразу под
полями режима, рядом с именем сеанса. Трафик снимается на машине-сервере — там, куда подключена
аппаратура; браузер только управляет. Всё — стандартной библиотекой Python
через `ctypes`, без сторонних пакетов.

**Сетевые карты сервера**: имя, описание, адреса IPv4/IPv6 с префиксом, MAC,
состояние (RFC 2863: работает, отключена, нет связи…), скорость, занята ли
картой чужим захватом.

- Linux — `/sys/class/net/<карта>/` (`address`, `operstate`, `speed` в Мбит/с,
  `mtu`, `type`, `carrier`) и адреса из `getifaddrs(3)`; если служба не пускает
  netlink (systemd `RestrictAddressFamilies`) — запасной путь: ioctl
  `SIOCGIFADDR`/`SIOCGIFNETMASK` и `/proc/net/if_inet6` (длина префикса в нём
  шестнадцатеричная).
- Windows — `GetAdaptersAddresses` (iphlpapi.dll): понятное имя («Ethernet 2»),
  описание, адреса с `OnLinkPrefixLength`, MAC, `OperStatus`, `ReceiveLinkSpeed`.
  Строки WCHAR читаются как UTF-16LE вручную, раскладка — по iptypes.h (x64:
  структура 448 байт) и проверена тестом на поддельном буфере. Устройство Npcap
  (`\Device\NPF_{GUID}`) сопоставляется карте по GUID. Петля Npcap (`\Device\NPF_Loopback`, GUID
  адаптера у неё нет) — петлевой карте Windows, а без неё — отдельной картой
  (снимает, как и петлю Linux, только создатель системы).

**Режимы**

| Режим | Как | Права | Что видно |
|---|---|---|---|
| Приём UDP | сокет на адрес:порт (до 16 портов, диапазон «5002-5004»), по желанию — вступление в группу многоадресной рассылки | не нужны | датаграммы на эти порты; заголовки Ethernet/IP/UDP синтезируются (RFC 894/791/768, суммы по RFC 1071), MAC — нули; адрес получателя при «все адреса» — из `IP_PKTINFO` (Linux), иначе нули |
| С карты: Npcap (Windows) | `wpcap.dll` из `%SystemRoot%\System32\Npcap` полным путём; `pcap_open_live`, BPF (`pcap_compile`/`pcap_setfilter`), `pcap_next_ex`, `pcap_stats` | по установке Npcap: с `/admin_only` — администратор | все кадры карты, неразборчивый режим по желанию |
| С карты: сырой сокет SIO_RCVALL (Windows без Npcap) | `AF_INET/SOCK_RAW` на адресе карты, `RCVALL_ON` | администратор (иначе WSAEACCES) | только IPv4 (без ARP и IPv6); уровень Ethernet синтезируется |
| С карты: libpcap (Linux) | как Npcap; библиотека из системы или `capture_libpcap` | root или `CAP_NET_RAW` | все кадры |
| С карты: AF_PACKET (Linux) | `socket(AF_PACKET, SOCK_RAW, ETH_P_ALL)`, `PACKET_MR_PROMISC`, `PACKET_STATISTICS`; BPF из libpcap навешивается `SO_ATTACH_FILTER`, если libpcap есть | root или `CAP_NET_RAW` | все кадры; на петле исходящие не дублируются (как в libpcap) |

«Выбрать самому» берёт первый доступный способ: Npcap/libpcap, затем
AF_PACKET или SIO_RCVALL. Недоступный способ показан с причиной словами:
«Npcap не установлен…», «нужен запуск от администратора / root», «порт занят
другой программой», «такого адреса нет у этой машины».

**Фильтр** (для захвата с карты): протокол (UDP, TCP, ICMP, IPv4, IPv6, ARP),
IP источника, IP получателя, порт любой стороны. Он же — выражение BPF
(pcap-filter(7)), собранное только из проверенных значений; кадры с метками
VLAN (802.1Q/802.1ad) отбираются тем же выражением после `vlan`. Где BPF нет,
отбирает программа по тем же правилам; отброшенное — в счётчике «отфильтровано».

**Без пределов — часами и сутками.** Длительность, число пакетов и объём —
только если человек задал их сам (или администратор поставил потолки
`capture_max_seconds` / `capture_max_mb`; по умолчанию 0 — потолков нет).
Без них захват идёт, пока его не остановят кнопкой «Стоп», пока сервер не
выключат — или пока на диске есть место: когда свободного места становится
меньше запаса `capture_disk_reserve_mb` (по умолчанию 1024 МБ), захват
останавливается сам с причиной «мало места на диске сервера», записанное
остаётся целым. Перед стартом проверяется то же (с учётом того, что ещё
допишут идущие захваты с пределом объёма).

По «Стоп» то, что ядро уже приняло до команды (буфер сокета до 32 МБ), дочитывается
и пишется (не дольше 10 с — поток, который не кончается, дочитывался бы вечно,
тогда в заметках честно сказано, что остаток буфера не записан; у libpcap/Npcap
дочитывания нет: `pcap_next_ex` без трафика может ждать), так что отправлено =
принято + отброшено и после остановки на ходу.

Счётчики обновляются вживую: пакетов, объём, пакетов/с и бит/с за последние
секунды, отброшено ядром/драйвером (`pcap_stats`, `PACKET_STATISTICS`,
счётчик сокета `sk_drops` через `SO_MEMINFO`; `SO_RXQ_OVFL` у датаграммы видит лишь потери до её
постановки в очередь, а не в конце всплеска), отфильтровано, порты UDP получателя, число кусков и место на
диске. Захват живёт на сервере: закрытая или перезагруженная страница снова
подключается к его ходу (`#/zahvat/<ид>`).

**Запись кусками** — как `dumpcap -b` (doc/man_pages/dumpcap.adoc): пакеты
сразу уходят на диск цепочкой файлов pcapng `куски/000000.pcapng`,
`000001.pcapng`…; новый кусок — когда текущий набрал заданный объём (по
умолчанию 64 МБ, не больше `max_upload_mb`, чтобы кусок открывался в
анализаторе), 100 000 пакетов или заданное число секунд. **Кольцо** («хранить
последних N кусков») удаляет старшие — для круглосуточного наблюдения. В памяти
пакеты не копятся, поэтому память сервера не растёт, сколько бы ни шёл захват.
Каждый кусок — самостоятельный pcapng: SHB (ОС, приложение), IDB (тип канала,
snaplen 262144, имя и описание карты, MAC, адрес, скорость, фильтр,
`if_tsresol` = 6 — микросекунды), EPB на каждый кадр, в конце — ISB со
счётчиками с начала захвата (начало и конец, принято, отброшено, прошло фильтр,
записано: «starting at the beginning of the capture», draft-ietf-opsawg-pcapng).
Склейка кусков подряд — тоже файл pcapng (секции идут одна за другой): так
выгружается «Скачать pcapng» (обычной ссылкой: браузер пишет гигабайты
многочасового захвата прямо в файл, не держа их в памяти страницы). Оборванный кусок (сервер выключили) читается до
последнего целого блока. Закрытый кусок дописывается строкой в указатель
`куски.jsonl` (номер, пакетов, байт, время первого и последнего пакета).
Хранится в `data_dir/zahvat/<ид>/`; имя папки создаёт сервер, путь от
пользователя не принимается. Последние 10 захватов на человека; в резервную
копию не идут.

**Анализ пакетов вживую.** Галочка «анализ пакетов вживую» (по умолчанию
включена) или кнопка **«Анализ пакетов вживую»** на странице идущего приёма
открывают запись «Анализа пакетов», которая читает части записи следом за
приёмом — прямо из папки приёма, без склейки и копий файлов: список пакетов,
дерево протоколов, статистика и фильтр растут на глазах, часами (21.6). Разбор —
отдельный процесс, приём от него не зависит: если разбор отстаёт (Python
разбирает тысячи пакетов в секунду, а принимает сотни тысяч), он честно отстаёт,
а части, которые кольцо удалило раньше, чем он до них дошёл, пропускает и пишет
об этом в заметки. Приём остановили — анализ дочитывает последнюю часть и
становится обычной законченной записью.

**Обработка на лету** (галочка, по умолчанию выключена) — повторная обработка
(21.8) следом за записью: нужна, когда нагрузку порта UDP надо сразу писать в
файл.

**Обработка**

- **Весь приём — в анализ пакетов.** Весь приём одной записью «Анализа пакетов»
  — и законченный, и идущий (тогда вживую): части читаются по порядку прямо из
  папки приёма, без предела размера (только место на диске и `pakety_max_mb`);
  кольцо удалило часть — это видно в заметках.
- **Части записи — в анализ пакетов.** Многочастный приём открывается и по
  частям, постранично: список частей (номер, пакетов, объём, время) с кнопкой
  «В анализ пакетов» у каждой; закрытые части идущего приёма открываются сразу
  (пишущаяся — когда закроется). У такой записи — переход к соседним частям.
  Одновременно открыто не больше трёх частей одного приёма (прочие открываются
  заново по щелчку).
- **«Нагрузку порта — в сессию потоков…»** — тела датаграмм выбранного порта
  UDP (и, по желанию, одного отправителя) подряд, в порядке прихода, одним
  массивом сессии, сразу видным битами. Срез: ничего; N байт в начале каждой
  датаграммы; заголовок RTP целиком (RFC 3550 §5.1: 12 + 4·CC байт, расширение
  при X, дополнение при P). «Упорядочить по номеру RTP» — по расширенному
  номеру (переходы через 65535), повторы убираются, пропуски и перестановки
  пишутся в происхождение массива; скачок больше 3000 номеров считается
  разрывом нумерации (MAX_DROPOUT, RFC 3550 §A.1); несколько SSRC идут друг за
  другом. Порядок бит в байте — старший первым (как в сети), младший или
  «определить». Фрагменты IP не собираются — их число в заметках.

**Права и журнал.** Захватывать может должность не ниже `capture_min_role`
(по умолчанию `engineer` — инженер и выше; `off` — никто; гость — никогда).
Отказ, запуск (и неудачный — с причиной), остановка, передача в «Пакеты» и в
сессию, удаление пишутся в журнал (`zahvat.denied`, `zahvat.start`,
`zahvat.stop`, `zahvat.pakety`, `zahvat.session`, `zahvat.delete`). Захват
видит его автор; начальник группы и выше может посмотреть и остановить чужой
(карта бывает нужна другому), обрабатывать — только автор.

**Защита от перегрузки.** Один захват на карту и один на порт UDP; на сервере
одновременно не больше 4 захватов, у человека — 2; перед стартом проверяется
свободное место (предел объёма, если задан, плюс запас); заданный предел объёма
не переходится ни на байт (с заголовками и итогами всех кусков). Приём UDP
просит у ядра буфер 32 МБ (`SO_RCVBUFFORCE` мимо `net.core.rmem_max`, если у
службы есть `CAP_NET_ADMIN`, иначе `SO_RCVBUF` — ядро урежет до предела).

**Нагрузочная проверка** (стенд: 4 ядра, заняты и другими задачами): поток UDP
на `lo` 300 Мбит/с (датаграммы 1400 байт, два процесса-отправителя) десять с
половиной минут через настоящий сервер и API, куски по 64 МБ, кольцо 16,
обработка на лету отдельным процессом. Память процесса сервера — на одном
уровне всё время (см. таблицу ниже), процесса прогона — тоже; отправлено =
принято + отброшено (отброшенное ядром при занятом процессоре — в счётчике
«отброшено», `SO_RXQ_OVFL`).

| Прошло, с | Память сервера, МБ | Память прогона, МБ | Принято пакетов | Отброшено ядром | Мбит/с | Кусков | На диске, МБ |
|---|---|---|---|---|---|---|---|
| 10 | 127 | 41 | 267 456 | 0 | 307 | 6 | 376 |
| 131 | 131 | 41 | 3 437 953 | 61 055 | 308 | 76 | 999 |
| 251 | 131 | 42 | 6 664 856 | 65 256 | 330 | 147 | 997 |
| 372 | 131 | 42 | 9 185 593 | 747 411 | 250 | 203 | 961 |

Итог за 635,6 с: отправлено 16 969 216 датаграмм = принято 15 887 015 +
отброшено 1 082 201 (6,4 %: отброшенное пришлось на минуты, когда процессор
стенда был занят другими задачами, и честно посчитано), записано 21,3 ГБ со

прогон, перечислены в его заметках. Без кольца куски не удаляются, и прогон
догоняет захват после остановки.

**Повторная нагрузочная проверка после слияния** (тот же стенд, но занятый
чужими задачами сильнее: средняя загрузка 12–16 на 4 ядра; 300 Мбит/с на `lo`,
датаграммы 1400 байт, два отправителя, 632 с, куски 64 МБ, кольцо 16, обработка
на лету): память процесса сервера — 118 МБ от первой до последней минуты,
процесса прогона — 42 МБ. Отправлено 16 874 983 = принято 7 802 325 + отброшено
9 072 658 — сходится до датаграммы; записано 11,5 ГБ в 172 куска, кольцо
удалило 156, на диске всё время около 1 ГБ. Доля отброшенного велика потому,
что процессор стенда был занят чужими задачами (поток приёма получал меньше
ядра): она честно в счётчике. Этот прогон нашёл две ошибки подсчёта — обе
исправлены с тестами: `SO_RXQ_OVFL` не видит потерь после последней принятой
датаграммы (теперь — `sk_drops` через `SO_MEMINFO`), а «Стоп» выбрасывал
то, что лежало в буфере сокета (теперь дочитывается).

**Установка.** Windows: Npcap ставится отдельно из комплекта (см. 15.10);
без него — сырой сокет, и тогда сервер нужно запускать от администратора.
Для приёма UDP разрешите входящий порт в брандмауэре. Linux (служба systemd):
для захвата с карты — `CAP_NET_RAW` и семейство `AF_PACKET`, см. 10.6.

## 21.8. Повторная обработка: старт, пауза, стоп — как у проигрывателя

У любой записи «Анализа пакетов» (свёрнутый блок «Повторная обработка…» над
фильтром — раскрывается, когда нужен) и у приёма с сети есть панель
**«Повторная обработка»** (по умолчанию — с максимальной скоростью): захват (или файл) заново проходит через ту же обработку, что и
анализатор, — разбор по уровням с правилами «разбирать как» и «Декодировать
как» (21.9), дерево протоколов (пакеты, байты и доля на каждом узле), порты,
диалоги IP, ошибки разбора — и через **выходные данные**: нагрузку выбранного
порта UDP (срез N байт или заголовка RTP, отправитель, упорядочивание по номеру
RTP в окне из 64 датаграмм на SSRC) в файл. Всё растёт по ходу: страница
видит ход дважды в секунду.

- **«Старт»** — начать прогон; **«Пауза»** / **«Продолжить»**; **«Стоп»**;
  **«Сначала»** — заново с начала, с текущими правилами, скоростью и выходными
  данными (так прогоняют заново после смены настроек разбора).
- **Скорость**: «как записано» (по отметкам времени пакетов, ×1), ×0,5, ×2, ×5,
  ×10, ×100 или «максимально»; меняется на ходу.
- Выходные данные — «Скачать .bin» или **«В сессию потоков…»** (битовым
  потоком, как «Добавить файлы»; порядок бит в байте — старший, младший или
  «определить»).

Прогон идёт на сервере **отдельным процессом** (`capture_worker_process`,
по умолчанию включено): разбор пакета на Python занимает десятки и сотни
микросекунд и в процессе сервера отнимал бы время у приёма захвата и у страниц
других людей. Команды процессу — строками JSON в его stdin; закрытый stdin
(сервер выключился) — стоп. Не запустился процесс — прогон идёт потоком в
сервере с тем же результатом. Память прогона не растёт с длиной захвата:
пакеты не копятся, у дерева (3000 узлов), портов (64) и диалогов (256) —
потолки, сверх них — «прочие». Страница после перезагрузки снова находит свой
прогон. Одновременно — не больше 4 прогонов на сервере и 2 у человека; хранятся
последние 10 на человека (`data_dir/progon/`, в резервную копию не идут). Места
на диске меньше 256 МБ — прогон с выходными данными останавливается сам.

Захват с сети прогоняется **следом за записью**: прогон читает куски по мере
появления (незаконченная запись последнего куска — «пока нечего», чтение
продолжится с того же места), ждёт новых, пока захват идёт, и доходит до конца
после остановки.

## 21.9. «Разбирать как…»: одно окно правил, «убрать протокол»

Как «Decode As» и «Enabled Protocols» в Wireshark (Руководство пользователя
Wireshark, «Control Protocol Dissection», doc/wsug_src/wsug_customize.adoc).
Всё — в одном окне **«Разбирать как…»** (кнопка над записью и последний пункт
меню правой кнопки): сверху — правила по портам этой записи (порт TCP/UDP →
разборщик, «Разобрать заново»), ниже — ваши правила по протоколам и полям (для
всех ваших записей, повторной обработки и приёма с сети).
**Правая кнопка на протоколе** — в дереве полей пакета, в иерархии протоколов
(вкладка «Протоколы») и в дереве прогона:

- **«Убрать протокол X»** — байты X и всё вложенное — данными (разбор на X
  прекращается, как у выключенного протокола); можно — только поверх
  протокола ниже («убрать UDP только поверх IPv4»);
- **«Снять заголовок X, вложенное — как обычно»** — заголовок X становится
  данными, вложенное разбирается следующим уровнем как обычно; или
  **«…вложенное разобрать как…»** — выбранным разборщиком;
- **«Разобрать X как…»** — на месте X — другой разборщик;
- правая кнопка на **поле** (например, «Порт получателя» UDP, «Тип» Ethernet)
  — **«Разобрать вложенное при udp.port = 5004 как…»** и «Не разбирать
  вложенное при …»: правило по полю (порт TCP/UDP, EtherType, номер протокола
  IP, PPID SCTP, VLAN, тип сообщения GTP и любое другое поле протокола);
  «Правило по полю…» — то же вручную, с подсказками полей.

Разборщик выбирается **из списка всех разборщиков анализатора** — канальные,
по EtherType, по номеру протокола IP, поверх UDP/TCP/SCTP/PPP/LLC, со своими
местами («UDP порт 53») — **с поиском** по названию, описанию и месту; первым
в списке — «Данные — не разбирать». Разборщики, которые добавляют модули
`protokoly/*`, попадают в список сами.

Правила — **свои у каждого человека** (`data_dir/dekodirovat_kak/<ид>.json`,
идут в резервную копию), до 64: список «Правила «Декодировать как»» —
включить, выключить, удалить. Правило для того же места заменяет прежнее.
Правила применяются ко всему захвату и сразу: захват «Пакетов» разбирается
заново, прогон начинается сначала; новые захваты (загрузка, куски захвата с
сети) разбираются с правилами с самого начала; повторный прогон — тоже. В
дереве прогона видно, сколько пакетов разобрано по правилам.

**Как устроено.** Точка в ядре разбора одна: `razbor.разобрать_пакет`
передаёт пакет в `dekodirovat_kak.разобрать_по_правилам`, если в правилах
«разбирать как» есть ключ `"правила"`. Разбор идёт теми же разборщиками:
подкласс `Разбор` сверяет с таблицей правил создание каждого уровня
(`Разбор.уровень` — через него проходит каждый протокол); если правило велит на
этом месте другое, создание прерывается исключением-«поворотом», стек
разборщиков сворачивается до входа, и разбор продолжается с того же смещения
нужным разборщиком. Конец вложенного — по нагрузке, отмеченной уровнем ниже,
или по длинам UDP (RFC 768), IPv4 (RFC 791, Total Length) и IPv6 (RFC 8200,
Payload Length) — дополнение короткого кадра Ethernet в данные не попадает.
Разборщик, которому данные не подошли, откатывает свои уровни, пакет получает
ошибку «разобрать как X: данные не подошли», а байты — уровнем «Данные».
Больше 8 поворотов на пакет не бывает (правило «UDP 4789 → Ethernet» внутри
себя снова встретило бы UDP 4789). Таблицы разборщиков `razbor`/`prilozh`/
`protokoly` не меняются; реестр строится из них заново, когда они пополнились.

перечитывать имена каналов после 64-го — у записи, где каналов больше, новые

Эквивалентные — те, что поведения не меняют (по разделам):

- **Аннотации** `X | None` → `X & None` (все модули): при `from __future__ import
  annotations` аннотации, и у dataclass тоже, не вычисляются.
- **nakopitel.py.** «Раньше/позже» `<` → `<=` при выборе начала и конца диалога и
  узла дерева (`время < з[4]`, `время > з[5]`, `время_от`, `время_до`): при равенстве
  записывается то же значение. Ключ пары `(а, б) if а <= б` → `<`: при `а == б` обе
  ветки дают `(а, а)`. Сторона пакета без адресов `0` → `1`: у такого пакета нет
  ключа пары, сторона не читается (`_узел` выходит раньше). Счёт портов служб
  `+= 1` → `+= 2`: из него берётся только порядок (`most_common(5)`), удвоение всех
  счётчиков порядка не меняет. `split(":", 1)[-1]` → `[1]`: при двоеточии в тексте
  частей ровно две. `most_common(1)[0]` → `most_common(2)[0]`: первый тот же. Корень
  дерева `not путь and у is корень` → `or`: обход зовётся с корнем и пустым путём,
  дальше — с детьми и непустым, обе формы совпадают.
- **fayly_ssylki.py.** `mkdir(exist_ok=True)` → `False`: «уже есть» — `OSError`, он
  перехвачен, папка та же. Ранг человека без ранга `0` → `1` и ранг папки с
  неизвестной должностью `0` → `1`: в штатном расписании нет ранга 1 (0, 10, 20…),
  а папка с неизвестной должностью не показывается вовсе. Предел времени поиска
  `>=` → `>`: равенство двух отметок монотонных часов не наступает.
- **chtenie.py.** Растущий файл короче `4` байт → короче `3`: три байта — не
  сигнатура pcap/pcapng, и следующая проверка («проба .sig ещё не набралась») так же
  велит ждать.
- **hranilishe.py.** Выбор способа чтения индекса (одним куском или по записи:
  `ПОДРЯД_ДО`, `4 * len(номера)`, `+ 1` к концу промежутка) и размеры порций и кэша
  (`ПОРЦИЯ`, частота сверки отпечатка `< 1.0`, проверка «в порции» `<=`/`+`) —
  только скорость: оба пути дают те же записи (тест сверяет их при `ПОДРЯД_ДО = 0`).
  `zip(…, strict=True)` → `False`: длины равны по построению. Чтение «на один больше»
  (`номер + 2` в `кадр`/`сводка`) — берётся первый элемент. Пустой промежуток
  `до <= от` → `<`: чтение нуля байт даёт тот же пустой ответ. Граница
  `номер <= число()` в `сводка` и `i <= len` в `Ряд`: то же `IndexError`, только из
  списка. Обрезка прочитанного индекса до целых записей (`//` → `*`) — защита от
  гонки, которой при записи индекса целыми записями не бывает. Отпечаток `or 1` →
  `or 2`: обе CRC-32 равны нулю — не встречается. Начальное «записано каналов» `−1`
  → `−2`: любое отрицательное заставляет записать список. Сброс `>=` → `>`: равенство
  отметок часов. `ensure_ascii=False` → `True`: тот же JSON после чтения.
- **raboty.py.** Ожидание процесса и работы `5` → `4`/`6` с — время, не итог.
  `ensure_ascii=False` → `True` в команде процессу: та же команда после чтения.
  Порядок работы по умолчанию `0` → `1`: `поставить` всегда задаёт свой.
  `_под_замком=False` → `True`: без замка снятие то же, пока два потока не правят
  очередь в одно мгновение (тестом гонку не поймать — замок оставлен). `max(2, min(16, 2 * ядер))` → `max(1, …)`:
  при любом числе ядер `2 * ядер ≥ 2`. Счёт идущих у человека `get(…, 0) + 1` →
  `get(…, 1) + 1` или `+ 2`, давность обслуживания нового человека `−1` → `−2`: сравнения
  те же (сдвиг и растяжение не меняют порядок, «ещё не обслуживался» остаётся
  меньше любого номера запуска).
  Не проверяются на этом стенде (Linux): флаги процесса Windows
  (`CREATE_NO_WINDOW | BELOW_NORMAL_PRIORITY_CLASS`, умолчания `getattr` и
  `sys.platform == "win32"`) — четыре мутанта; и `заняты += 1` → `+= 2` — вторая
  работа из очереди запускается не в том же обходе, а в следующем (через ≤ 0,5 с),
  итог тот же.
- **app.js.** `Math.max(1, прокрутка − видно)` → `max(2, …)` и
  `Math.max(0, строк − влезает + 1)` → `max(1, …)` в сжатом списке: сжатие включается
  только при высоте списка больше 8 млн px — там оба выражения в миллионы раз больше
  предела.
