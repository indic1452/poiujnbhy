# 21. Анализатор сетевых пакетов

Страница **«Пакеты»** (меню «Знание») — разбор сетевого захвата по уровням на
сервере отдела, без интернета и без установки программ на рабочие места:
открывается в браузере, как всё рабочее место.

## 21.1. Откуда берутся пакеты

- **Файл захвата**: pcap (микро- и наносекундный, оба порядка байт), pcapng
  (блоки SHB/IDB/EPB/SPB, разрешение времени интерфейса), `.sig` (кадры с
  двухбайтовой длиной — разметка определяется сама).
- **Из разбора потока**: у этапа, после которого получились пакеты IP или
  кадры, — кнопка **«Пакеты»**. Кадры без канального заголовка (после HDLC,
  из .sig) разбираются «по признакам»: IP по контрольной сумме заголовка,
  PPP по `FF 03`, Cisco HDLC, Ethernet по типу, затем канальные протоколы по
  признакам их стандартов — Frame Relay (адрес Q.922 и NLPID, LMI), LAPD
  (EA, SAPI 0/1/16/62/63, кадры I/S/U Q.921), LAPB без байта направления
  (адрес A/B/C/D, пакет X.25), AX.25 (позывные), MTP2 (LI сходится с длиной).
  Если разбор потока опознал канальный протокол по всей массе кадров, этап
  выгружается pcap с типом канала (MTP2 — 140, LAPD — 203, Frame Relay — 107,
  AX.25 — 3) и открывается сразу нужным разборщиком.

Разбор идёт в фоне; страница показывает, сколько пакетов разобрано. Захваты
хранятся (последние 30) и видны только тому, кто их открыл; в резервную
копию они не идут — пересчитываются из файла.

## 21.2. Что видно

- **Список пакетов**: номер, время от начала, источник, получатель, протокол,
  длина, сведения. Строка окрашена по семейству протокола (TCP, UDP, DNS,
  HTTP, TLS, ARP, ICMP, маршрутизация); ошибки — красным со знаком ⚠. Цвет
  дублирует столбец «Протокол» — он не единственный признак. ↑/↓ — по списку.
- **Дерево полей** — слева, с самого верха: уровни снизу вверх, у каждого
  поля — значение и место в байтах `[34…35]`. Всё прочее о пакете — справа
  от дерева: заголовок с действиями («Следовать за потоком», «Разбирать порт
  как…», «Спросить помощника о пакете»), ошибки, вид байт и дамп. Щелчок по
  полю подсвечивает его байты в дампе; наведение на байт дампа подсвечивает
  поле, из которого он прочитан. Над дампом — готовое выражение фильтра для
  выбранного поля: **«Отобрать такие»**, **«Кроме таких»**.
- **Описание — справа.** Пояснения к разделу и вкладкам (матрица байт,
  протоколы, неизвестные форматы) — в правой панели «Описание», свёрнутой по
  умолчанию; открывается щелчком по ручке у правого края.
- **Дамп байт**: HEX, DEC, BIN или ТЕКСТ (CP1251 для кириллицы), порядок бит
  в байте — старший или младший первым.
- **Контрольные суммы** пересчитываются: IPv4 (заголовок), TCP/UDP (с
  псевдозаголовком IPv4/IPv6), ICMP, ICMPv6, SCTP (CRC32c). Неверная —
  красным и в списке ошибок. У TCP «не сошлась» бывает и у исправного пакета:
  захват на передающем узле до подсчёта суммы сетевой картой — так и написано.
- **Фрагменты IPv4 собираются**: к последнему фрагменту добавлен разбор
  собранного пакета и его собственный дамп.

## 21.3. Фильтр

Язык в духе Wireshark, но свой и безопасный:

| Выражение | Что отбирает |
|---|---|
| `tcp`, `dns`, `arp`, `ip`, `vlan` | пакеты с этим уровнем |
| `ip.addr == 10.0.0.0/8` | адрес (любой из двух) в подсети |
| `ip.src == 10.1.1.1`, `ipv6.dst == 2001:db8::1` | источник, получатель |
| `tcp.port == 443 or udp.port == 53` | порты |
| `port in {53 123 161}` | порт TCP, UDP или SCTP из списка |
| `dns.qry.name contains "mail"` | подстрока без учёта регистра |
| `http.host matches "^mail\."` | регулярное выражение |
| `frame.len > 1000 and not arp` | длина, логика `and`/`or`/`not`, скобки |
| `http.request.method == "POST"` | любое поле из дерева (ключ — в подсказке поля) |
| `frame[12:2] == 0800` | байты 12–13 кадра (HEX: `0800`, `08:00`, `0x0800`; десятичное — `2048`) |
| `payload[0].hi == 0xA`, `payload[0].lo == 5` | полубайты первого байта нагрузки верхнего уровня |
| `frame contains ff:d8:ff`, `payload contains "JFIF"` | последовательность байт или текст |
| `expert` (или `ошибки`) | пакеты с ошибками (суммы, обрывы) |
| `данные` (или `data`) | нагрузка, которую ни один разборщик не взял |

Статистика на всех вкладках считается по отобранным пакетам.

Ошибка в выражении видна по мере набора — поле краснеет, под ним сказано,
что не так, ещё до «Отобрать». Применённые фильтры запоминаются в этом
браузере (последние 20) и предлагаются при наборе. Клавиши: **/** — к
фильтру, **Esc** — вернуть применённый; в списке пакетов **↑/↓**,
**PageUp/PageDown** (по 20), **Home/End**.

## 21.3а. Разбирать как

Служба на нестандартном порту (HTTP на 8888, DNS на 5000, свой SIP) по
таблице портов не узнаётся. Кнопка **«Разбирать как…»** в шапке захвата
или **«Разбирать порт N как…»** у пакета задаёт правило «UDP/TCP порт →
разборщик»; захват разбирается заново в фоне, фильтры и статистика видят
новый разбор. Разборщик и по выбору аналитика проверяет, что данные его: не
подошли — это видно в ошибках пакета («разбирать как BGP (порт 8888): данные
не подошли»), и разбор идёт дальше обычным путём. «Не разбирать (данные)» —
когда угадывание по содержимому ошибается. Правило снимается крестиком.

## 21.4. Вкладки

- **Обзор** — главное одним взглядом, считается само: пакеты, объём,
  длительность, средняя скорость, пакеты с ошибками, объекты и файлы (плитка
  и карточка «сколько каких видов»);
  протоколы с долями, главные диалоги IP, имена DNS, серверы TLS (SNI), узлы
  HTTP, виды ошибок, неразобранная нагрузка по портам. Блок **«На что
  посмотреть»** — приметы с кнопкой отбора: протоколы открытым текстом (HTTP,
  FTP, Telnet, POP3, IMAP, SMTP, SNMP, TFTP, Syslog), DNS-запросы без ответа
  (сопоставление по идентификатору и порту клиента), суммы TCP, не сошедшиеся
  у большинства пакетов (захват на передающем узле, а не порча), больше всего
  неразобранного, найденные файлы. Любая строка обзора — щелчок: отбор пакетов
  или переход на нужную вкладку.
- **Протоколы** — иерархия протоколов: сверху схема-«сосулька» (ширина — доля
  пакетов или байт внутри узла, ряд — уровень вложенности; двойной щелчок —
  приблизить узел, «хлебные крошки» — назад), ниже дерево-таблица со всеми
  столбцами Wireshark «Protocol Hierarchy» (% пакетов, пакеты, % байт, байты,
  бит/с, % от родителя, кончаются здесь — пакеты и байты), сортировкой по любому
  столбцу, порогом «скрыть мельче N %», поиском, выгрузкой в CSV и JSON (раскрытие,
  клавиши ↑ ↓ ← → и Enter) и карточка узла: доли детей сегментной полосой,
  направления по адресам, диалоги и узлы, первый и последний пакет, выходные
  данные узла (объекты, pcap, поля, потоки — см. 21.4а); кнопки «Показать
  пакеты», «Исключить», «И к фильтру», «Приблизить на схеме». Цвет — уровень
  протокола (канальный, сетевой, транспортный, прикладной), рядом всегда подпись.
- **Диалоги** — Ethernet, IP, TCP, UDP: пакеты и байты в каждую сторону,
  начало, длительность, протоколы; щелчок — отбор пакетов диалога.
- **Узлы** — адреса: отправлено, получено, службы (порты < 1024).
- **Матрица байт** — пакеты строками, байты столбцами, выравнивание от начала
  кадра или от нагрузки верхнего уровня, окно по 16–256 столбцов. Над
  столбцами — **профиль энтропии**: низкие столбики — постоянные поля, типы,
  синхрослова; высокие — данные. Щелчок по заголовку — **статистика столбца**
  (или поля 2–8 байт): значения по частоте (щелчок — отбор), энтропия,
  различных значений, полубайты, доля единиц по битам и вывод: «постоянное
  поле», «счётчик +1», «растёт с шагом», «поле длины: длина пакета − k»,
  «поле типа», «похоже на случайные данные». **Правая кнопка** на ячейке —
  отбор по байту, полубайту, полю, «кроме», статистика; на заголовке —
  статистика, начать матрицу с этого байта. Вид — HEX/DEC/BIN/ТЕКСТ, порядок бит.
- **Время** — пакеты или байты за интервал (одна величина за раз), с таблицей.
- **DNS** — запросы и ответы: клиент, сервер, имя, тип, ответы, код.
- **HTTP** — запросы с ответами: метод, узел, адрес, код, агент.
- **TLS** — ClientHello: имя сервера (SNI), ALPN, версии.
- **Объекты и файлы** — всё, что передано: тела HTTP и части форм, файлы FTP
  и TFTP, письма и вложения, звук и видео RTP, сообщения WebSocket, JSON,
  файлы по сигнатуре в неразобранных потоках; вид по содержимому, опись
  архивов, скачивание по одному и ZIP с описью (подробно — 21.4а).
- **Ошибки** — по видам, с номерами пакетов.
- **Неизвестные форматы** — нагрузка без известного разборщика по группам
  (транспорт и порт службы): поля неизвестного формата (постоянные, счётчики,
  длины, типы) и CRC вслепую — тот же анализ, что у кадров потока.

**Следовать за потоком** (у пакета TCP/UDP/SCTP): нагрузки в обе стороны по
порядку, у TCP — по номерам последовательности, повторы и перекрытия
отбрасываются; текстом или HEX; кнопка отбирает пакеты потока.

**Выгрузка**: отбор — в pcap, pcapng, CSV или JSON; «Выходные данные» — всё
сразу одним ZIP с описью (21.4а).
**Спросить помощника** — о захвате (иерархия, диалоги, ошибки) или о пакете
(всё дерево полей с местами в байтах): помощник объясняет по RFC и стандартам
из библиотеки.

## 21.4а. Объекты и файлы: что выдаётся в файлы

Вкладка **«Объекты и файлы»** выдаёт всё, что передано в захвате, — как «Экспорт объектов» в
Wireshark, только шире: не одни тела HTTP, а файлы FTP и TFTP, письма с вложениями, звук и видео
RTP, сообщения WebSocket, значения JSON и файлы, найденные по сигнатуре в том, что протоколы не
разобрали. Объекты строятся из пакетов под текущим фильтром отбора. У каждого объекта есть вид, имя,
тип, длина, поток, пакеты, заметки и сами байты. Имя берётся из Content-Disposition, адреса, команды
FTP, имени TFTP или вложения; если его нет, имя составное — из потока и места. Заметки говорят о
снятом сжатии, обрыве, пропусках и дырах в потоке.

Таблица на вкладке:

- фильтр по виду;
- щелчок по строке переводит к первому пакету объекта;
- у каждой строки есть кнопка «Скачать»;
- есть кнопки «Скачать всё (ZIP)» и «Скачать отобранные виды (ZIP)».

Звук RTP слушается прямо в строке (`<audio>`). JSON показывается с отступами. Для ZIP и tar
(в том числе tar в gzip, bzip2 и xz) в раскрывающейся строке показывается опись членов, и любой член
можно скачать отдельно. RAR и 7z только опознаются, без описи. Колонка «Содержимое» показывает вид
по магии и структуре, а не по имени и Content-Type. Например, `.bin` с документом Word внутри будет
показан как «OLE2 (doc)». В обзоре есть плитка «Объекты и файлы» и карточка с числом объектов каждого вида.

Все таблицы и константы взяты из документов, с номерами разделов в комментариях кода
(`setevoy/obekty.py`, `potok/poisk.py`).

**ZIP объектов.** Имена в архиве уникальны: одинаковые получают «-2», «-3». «..», «/» и
управляющие символы заменяются, так что выйти из архива нельзя. Рядом лежит `опись.csv` со
столбцами: номер, вид, имя, «в архиве», тип, содержимое, длина, поток, пакеты, время, SHA-256, заметки.
В колонке «содержимое» стоит вид файла по содержимому.

**Выходные данные** — кнопка на странице и пункт обзора. Флажками отмечается, что выгрузить:

- отобранные пакеты в pcap и pcapng (SHB, IDB на каждый вид канала, EPB с микросекундами);
- список пакетов в CSV и JSON;
- полный разбор в JSON (дерево полей каждого уровня);
- поля по каждому протоколу в CSV;
- статистику в CSV и JSON: иерархия с долями, диалоги Ethernet, IP, TCP и UDP, узлы, время, DNS,
  HTTP, TLS, ошибки, неизвестные форматы;
- объекты по видам, звук и видео RTP, сырые потоки TCP и UDP по направлениям (`.bin`);
- отчёт-обзор в HTML (без внешних ресурсов, со светлой и тёмной темой) и текстом.

Рядом с каждым пунктом показано, сколько в нём будет. «Выгрузить отмеченное» собирает один ZIP с
папками `пакеты/`, `поля/`, `статистика/`, `объекты/<вид>/`, `rtp/`, `потоки/` и `отчёт/`, а также
`опись.csv` и `опись.json`. В описи для каждого файла указаны путь в архиве, что это, откуда (поток,
пакеты, протокол), время, размер и SHA-256. Что не вошло по пределу объёма, записывается в
`заметки.txt`. ZIP собирается во временном файле, поэтому большие выгрузки не держатся в памяти.

**Настройка выдачи** — кнопка «Настройка». Сервер настроек не хранит: всё запоминается у
пользователя в браузере и уходит параметрами запроса.

| Настройка | Параметр API | Значения |
|---|---|---|
| что отмечено по умолчанию | — | пункты «Выходных данных» |
| имена файлов | `names` | протокол (`0007-архив.zip`), поток и время (`0007-TCP_10.0.0.2_50000_…-20250929T130000-архив.zip`), только номер (`объект-0007.zip`) |
| снимать сжатие HTTP | `decompress` | да / нет (тело остаётся gzip) |
| тишина в пропусках RTP | `silence` | да / нет |
| звук | `audio` | WAV / сырые отсчёты кодека |
| видео | `video` | Annex B / NAL с 4-байтной длиной |
| JSON | `json` | с отступами / сжато |
| пределы | `maxobj`, `maxzip`, `maxcount` | МБ на объект, МБ на выгрузку, число объектов |
| порог дерева протоколов | — | скрыть узлы мельче N % (по умолчанию 0) |
| часовой пояс | `tz` | браузера, UTC или ±ЧЧ:ММ (минуты к UTC) — для времени в описи и отчёте |

**Дерево протоколов** (вкладка «Протоколы») показывает для каждого узла:

- % пакетов, пакеты, % байт, байты, бит/с (байты × 8 / длительность захвата);
- % от родителя по пакетам и байтам;
- сколько пакетов и байт кончаются на этом узле.

В каждой строке есть полоса доли. Сортировка возможна по любому столбцу. Поле «скрыть мельче N %»
прячет узлы, у которых и доля пакетов, и доля байт меньше порога. Поиск сохранён. Дерево
выгружается в CSV и JSON. Доли считаются так же, как Wireshark «Protocol Hierarchy»: от всех
пакетов и байт захвата под фильтром.

Карточка узла показывает:

- доли детей сегментной полосой (плюс «кончаются здесь») по пакетам и по байтам;
- соотношение направлений по парам адресов (А → Б и Б → А), число диалогов и узлов;
- первый и последний пакет;
- выходные данные узла: объекты этого протокола со скачиванием, пакеты узла в pcap и pcapng, поля
  в CSV и JSON, а у протоколов поверх TCP или UDP ещё и сырые потоки `.bin`.

API (права те же, что у соседних запросов страницы: только владелец захвата, чужой захват — 404, без входа — 401):

| Запрос | Что |
|---|---|
| `GET /api/pakety/{ид}/objects?filter=&kind=&path=` | список объектов, виды, отброшенное |
| `GET /api/pakety/{ид}/object/{n}?member=` | объект или член его архива; `Content-Disposition` с `filename*=UTF-8''` и запасным ASCII-именем |
| `GET /api/pakety/{ид}/objects.zip?filter=&kind=&path=` | ZIP объектов с описью |
| `GET /api/pakety/{ид}/export?format=pcap\|pcapng\|csv\|json\|dissect&path=` | пакеты и разбор |
| `GET /api/pakety/{ид}/fields?path=&format=csv\|json` | поля протокола |
| `GET /api/pakety/{ид}/streams.zip?path=` | сырые потоки |
| `GET /api/pakety/{ид}/stats?kind=protocol&path=` | соотношения узла |
| `GET /api/pakety/{ид}/stats-file?kind=&format=` | таблица статистики файлом |
| `GET /api/pakety/{ид}/report?format=html\|txt` | отчёт |
| `GET /api/pakety/{ид}/outputs`, `GET /api/pakety/{ид}/bundle.zip?items=` | пункты «Выходных данных» и общий ZIP |

Все запросы принимают `filter` и параметры настройки выдачи.

## 21.5а. Мутационная проверка

Каждый разборщик проверяется мутантами: в теле функций по одному меняются числа (±1), сравнения,
«и/или», «не», знаки, сдвиги, битовые операции и логические константы, и набор тестов должен
каждого такого мутанта «убить». Тесты сверяют не только итог, но и **раскладку полей** — ключ,
место, длину и сырое значение, выписанные вручную по стандарту, — и отказы разборщиков: чужие
данные дают «нет» без исключения и без уровней. Где мутант пережил тесты, добавлен тест или
упрощён код (лишняя проверка, которую перекрывает следующая, убрана — тогда и мутант пропадает).
Проверки вида «find() ≥ 0», где ноль невозможен по построению, и «split(…, 1)», где берётся лишь
первая часть, заменены на `index` с исключением и `partition` — у них нет неотличимых мутантов.
Мутационная проверка сама нашла ошибки: продолжение N-PDU в SNDCP падало, c= потока SDP
приписывался чужому потоку, оборванная личность в сводке GSM печаталась обрывком; у Reject
ANSI TCAP не требовались обязательные по ASN.1 идентификатор и параметр; многооктетные теги BER
(X.690 8.1.2.4) отвергались, хотя в параметрах MAP неопределённой длины они встречаются; признак
ESM под нулевым шифром читал байт за концом NAS-PDU; у MTP3 и SCCP тесты не сверяли места полей.

Объекты и файлы (`setevoy/obekty.py`, тесты `test_setevoy_obekty.py` и `test_setevoy_obekty_detali.py`),
база сигнатур (`potok/poisk.py`, `test_setevoy_signatury.py`), выгрузки (`setevoy/vygruzka.py`, новые части
`statistika.py`, `zahvaty.py` и запросов API — `test_setevoy_vygruzka.py`) и чистые функции страницы
(настройка выдачи, столбцы дерева — те же тесты в node) проверены так же. Мутационная проверка нашла:
текст длиннее 64 КиБ по-русски признавался «двоичными данными» (граница окна резала букву UTF-8);
у IFD TIFF и каталога OLE стояли произвольные пределы цепочки (256 и 4096) вместо защиты от петель;
имя в каталоге OLE читалось до конца поля, а не по длине; в `_mpa_кадры` проверка «длина < 4»
была недостижима. Проверки, у которых второй вариант неотличим (граница перед более строгой
проверкой, поиск «≥ 0», где ноль невозможен), переписаны без них: `index` с исключением, `partition`,
поиск, возвращающий None, стороны потока «целиком» по умолчанию.

Оставлены только **эквивалентные** мутанты — те, что не меняют поведения ни на каких данных:

| Где | Мутант | Почему эквивалентен |
|---|---|---|
| SSH: правдоподобие пакета | граница 35000 ± 1, «4 + длина» → «3 + длина», «(4 + длина) % 8» → «(4 − длина) % 8» | пакет вместе с полем длины кратен 8 (RFC 4253, 6): соседние с 35000 значения не кратны 8 и отвергаются этой же проверкой; кратность 8 у x и −x одна |
| SSH: отпечаток HASSH | `usedforsecurity=False` → `True` | флаг лишь разрешает MD5 в режиме FIPS, значение хеша то же |
| CFM (MPLS G-ACh) | проверка `тип in ДОП_ETHERTYPE` | для каналов G-ACh регистрирован только CFM; без проверки тот же путь |
| Jmirror | граница заголовка ± 1 | при нехватке данных разбор бросает исключение и откатывается — видимый итог тот же |
| DTAP: наименьшая длина | «< 5» → «< 4» | L3 из одного октета отвергает gsm.dtap по той же границе |
| RTP по SDP, UDPTL | «< 12» → «< 11», «< 4» → «< 3» | короче заголовка RTP (≥ 12 байт) и UDPTL с IFP ≥ 1 байта отвергает проверка длины заголовка и IFP |
| OSI: CLNP | «конец − м < 10» → «< 11», «≤ 10» | PDU из 10 октетов не вмещает длины адреса источника и отвергается проверкой адресов при любой границе |
| OSI: ES-IS | «конец − м < 10» → «< 9» | 9 октетов — без места под адрес: проверка адресов отвергает PDU, не читая за концом |
| OSI: TPDU | «конец − м < 2» → «< 3», «≤ 2» | TPDU из двух октетов (LI ≥ 2 требует трёх) отвергается проверкой постоянной части |
| OSI: NSAP | «≥ 9 октетов» → «≥ 8» | у 8 октетов запись «область.система.NSEL» и запись парами совпадают |
| Хуки ПЕРЕД_ПОРТАМИ | мутанты, превращающие отказ в чтение за концом | исключение в хуке откатывает уровни — итог тот же; такие места проверяются прямым вызовом разборщика |
| GTP-U: заголовки расширения | «есть октет PPI» `с[2:]` → `с[3:]`, то же у Long PDCP | содержимое заголовка — 4n − 2 октетов (2, 6, 10 …): «не меньше 3» и «не меньше 4» совпадают |
| Сборщик сегментов SCCP | аннотация `bytes \| None` → `bytes & None` | при `from __future__ import annotations` аннотации не вычисляются |
| Сигнатуры: обход tar, RAR 4, RAR 5 | «место − начало < ФАЙЛ_ДО» → «≤» | лишний проход на самой границе даёт длину больше предела — `_итог` и так вернёт 0; все прочие выходы в этом проходе — тоже 0 |
| Сигнатуры: длина кадра MPEG-аудио | 12000 → 12001, 144000 → 144001 | полным перебором версий, слоёв, скоростей и частот ISO 11172-3/13818-3: прибавка «скорость / частота» не переходит к следующему целому — длина та же (143999 отличим и убит) |
| Сигнатуры: TIFF, число записей IFD | «м + ifd + 2 > длины» → «+ 3», «≥» | если данные кончаются сразу за числом записей, следующая проверка (IFD целиком) всё равно даёт 0 |
| Сигнатуры: FLV, смещение данных | «< 9» → «< 8» | при смещении 8 «PreviousTagSize0» читается с самого байта смещения (0x08) — не ноль, отказ и так |
| Сигнатуры: Annex B, начало поиска следующего кода | м + 5 → м + 4 | байт м + 4 — заголовок NAL, проверенный на тип (не ноль): код начала с него начаться не может |
| Сигнатуры: Annex B, вложенная проверка | аннотация `int \| None` → `int & None` | аннотации не вычисляются |
| Сигнатуры: PDF, следующий «%PDF-» | начало поиска м + 5 → м + 4, м + 6 | байты м + 4 и м + 5 — «-» и цифра версии: подпись там начаться не может |
| Поиск в битах | сдвиги range(8) → range(9) | сдвиг 8 — тот же поток на байт дальше: находки совпадают по биту с находками сдвига 0 и отбрасываются как повторы |
| Объекты: аннотации полей и подписей | `X \| None` → `X & None` | при `from __future__ import annotations` аннотации (и у dataclass) не вычисляются |
| Объекты: номер объекта по умолчанию | 0 → 1 | номер присваивается всем объектам в `собрать` раньше любого чтения |
| Объекты: `zip(…, strict=…)` | False ↔ True | длины совпадают по построению (сводки и нагрузки, номера и пакеты, блоки и места) |
| Сборка TCP: знаковая разность номеров | внутреннее «+ 2³¹» → «− 2³¹»; внешнее «− 2³¹» → «+ 2³¹», «− 2³⁰», «− 2³²», «− 0» | «± 2³¹» внутри совпадают по модулю 2³²; внешнее вычитание — общий сдвиг всех отметок: порядок и разности те же (внутренний порог 2³⁰ отличим и убит тестом сегмента на 1,5 ГиБ позади) |
| Сборка TCP: пропуски по умолчанию | `заметки(начало=0)` → 1 | пропуск на месте 0 невозможен: первый кусок — опора |
| WebSocket: ключ маски | повторов ключа `n // 4 + 1` → `n * 4 + 1`, `n // 3 + 1`, `n // 4 + 2` | лишние повторы отрезаются срезом по длине данных |
| FTP: передача без объявленного канала | номер пакета объявления 0 → 1 | у такой передачи нет порта — она не сопоставляется, номер не читается |
| FTP, POP3: сравнение номеров пакетов разных сторон | «первый < объявлен» → «≤», «первый пакет сервера < первой команды» → «≤» | пакет принадлежит одной стороне: номера пакетов разных соединений и сторон не совпадают |
| SMTP, POP3: границы письма | поиск «CRLF.CRLF» с «− 2» → «− 3»; конец письма «+ 2» → «+ 3»; дальше «+ 5» → «+ 4» | байт перед CRLF строки DATA или «+OK» — буква, конец там не начнётся; лишняя точка строки конца снимается прозрачностью (RFC 5321, 4.5.2); следующая строка — пустая и пропускается |
| TFTP: имя запроса и окно | `данные[2:]` → `[1:]`; «номер < н» → «≤», «н < следующий» → «≤» | байт кода операции (0x01/0x02) — управляющий знак, `имя_файла` его убирает; на границах окна — сами запросы (код 1/2), а не DATA |
| TFTP, RTP: развёртка номеров | «+ модуль/2» → «− модуль/2» внутри взятия по модулю | разность — ровно модуль, остаток тот же |
| RTP: заголовок короче 12 байт | «< 12» → «< 11» | 11 байт без CSRC отсекает следующая проверка «начало нагрузки > конца» |
| RTP: G.711 без пропуска | «отсчётов < места» → «≤» | при равенстве вставляется ноль отсчётов тишины |
| RTP: преобладающий тип | `most_common(1)` → `most_common(2)` | берётся первый из списка — тот же |
| AMR с экономией полосы | «место + 6 > всего» → «+ 5»; неизвестный тип «−1» → «−2» | 4 + 6k и 8m чётны — разность 5 невозможна; любое отрицательное — отказ |
| Порядок объектов | ключ `пакеты[:1]` → `[:2]` | при равном первом пакете у объектов одного потока следующий тоже по порядку потока — сортировка (устойчивая) даёт тот же порядок |
| ZIP объектов | `compresslevel` 1 → 2 | меняется только степень сжатия, содержимое членов то же |

## 21.6. Скорость

Захват до 200 000 пакетов. Разбор — в фоне; сводки и поля для фильтров
хранятся на диске, подробный разбор пакета строится заново по щелчку (доли
миллисекунды). Разобранный захват держится в памяти (два последних), фильтр
запоминается — повторный отбор и статистика мгновенны.
