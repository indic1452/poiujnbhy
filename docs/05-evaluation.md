# 05. Оценка качества

Без измеримого качества система через полгода тихо деградирует, и никто не
заметит. Эвал-набор нужно собрать **до** первого дообучения.

## 5.1. Золотой набор

- 40–60 исторических писем, отобранных старшими инженерами как эталонные.
- Каждое письмо: исходные артефакты + факт-пакет (проверенный вручную) +
  финальный отчёт человека.
- Покрытие: все типы отчётов, все основные классы неисправностей, обязательно
  несколько «сложных» и несколько «данных недостаточно».
- Набор **заморожен** и не используется в обучении. Ни разу. Иначе через три
  итерации вы будете измерять переобучение.

Набор описывается JSON-манифестом: объект с полем `cases` (или просто список).
Обязателен в записи один `facts_path` — путь к проверенному факт-пакету;
`case_id` (иначе берётся из факт-пакета), `reference_path` и `outline_path`
необязательны. Слово `case` здесь историческое имя письма (док. 01, 1.2).
Относительные пути считаются от каталога манифеста, поэтому набор переносится
между машинами целиком. Образец — `examples/golden/manifest.json`. Прогон:

```
reportgen eval --golden examples/golden/manifest.json --out var/eval/run.md \
  --llm openai --base-url http://127.0.0.1:8000/v1 --index var/index.json
```

Без `--llm` берётся модель-заглушка: она удобна, чтобы проверить сам манифест
и пути, но качество ею не измеряют. Рядом с `run.md` кладётся `run.json` с
метриками по каждому письму — по нему удобно считать разбивки (например, по
направлениям, док. 13, 13.6).

Дополнительно держите «регрессионный набор» из 10–15 писем, которые гоняются
на каждое изменение промпта — быстрый прогон за 10 минут.

## 5.2. Метрики

### Автоматические (гоняются на каждый коммит)

Считает `reportgen eval`; пороги лежат в `evaluate.TARGETS`, и прогон помечает
набор непройденным, если среднее хоть по одной метрике ниже своего порога.

| Метрика | Как считать | Целевое значение |
|---|---|---|
| `numeric_fidelity` | доля чисел в тексте, присутствующих в факт-пакете | **100%**, иначе сборка красная |
| `fact_recall` | доля значимых находок (severity ≥ medium), упомянутых в отчёте; сравнение по стеммированным словам заголовка находки | ≥ 95% |
| `citation_precision` | доля ссылок `[S<N>]`, указывающих на реально выданный фрагмент. Что ссылка подтверждает мысль, машина не проверяет — это LLM-судья и выборочная ручная сверка (5.3, док. 13, 13.5) | ≥ 90% |
| `structure_compliance` | доля обязательных секций шаблона, оказавшихся в отчёте | 100% |
| `glossary_compliance` | доля терминов в канонической форме | ≥ 98% |
| `reference_similarity` | близость к эталонному отчёту человека (считается, если в манифесте задан `reference_path`) | порога нет, следят за трендом |
| Время прогона | `seconds_mean` в сводке | по SLA |

Объём секций в эти метрики не входит: за него отвечает верификатор. Он
предупреждает, когда секция короче 0,4 или длиннее 2,0 от целевого объёма
шаблона (`target_words`). Допуск нарочно широкий: узкий давал бы предупреждение
почти на каждом отчёте и его перестали бы читать.

Противоречий «выводы ↔ измерения» автоматической проверки пока нет — их ловят
вычиткой и LLM-судьёй. Заводить метрику `contradiction_rate` в отчётности,
пока её никто не считает, не стоит: она создаёт ложное ощущение контроля.

### Человеческие (раз в 2–4 недели, на 10–20 письмах)

| Метрика | Как считать |
|---|---|
| **Edit distance** | нормализованное расстояние «черновик → финал». Главная бизнес-метрика: она прямо про сэкономленное время. Следите за трендом, а не за абсолютом |
| **Time-to-report** | минуты от загрузки артефактов до утверждения |
| **Экспертная оценка 1–5** | корректность / полнота / стиль / готовность к отправке |
| **Слепое сравнение** | инженер получает два отчёта (человеческий и машинный, обезличенные) и говорит, какой лучше. Целевой ориентир на год: паритет в ≥ 40% случаев |

### Метрики RAG (отдельно от генерации)

Ломается чаще всего именно поиск, а винят модель.

- `recall@k` по размеченным парам «вопрос секции → нужный фрагмент» (соберите
  200–300 таких пар, это день работы инженера);
- доля секций, где реранкер поднял правильный фрагмент в топ-5;
- доля запросов, где не нашлось ничего релевантного (должна быть видима, а не
  замаскирована выдачей случайных чанков).

Этих метрик в харнессе нет: `reportgen eval` оценивает готовый отчёт, а не
поиск. Считают их своим скриптом поверх `GET /api/search` — он возвращает
фрагменты вместе с типом, направлением и ссылкой, и он же принимает фильтр
`domains`. У CLI-поиска (`reportgen search --index …`) фильтра по направлению
нет, поэтому для разбивки по направлениям берут API. Сама разбивка
обязательна — см. док. 13, 13.7.

## 5.3. LLM-судья: как не обмануть себя

Оценивать генерацию другой моделью можно, но:

- судья должен быть **другим** семейством моделей, иначе он любит свой стиль;
- давайте ему **критерий и эталон**, а не «оцени качество»;
- калибруйте: 50 примеров оцените людьми и судьёй, посчитайте согласие
  (Cohen's kappa ≥ 0.6 — можно доверять трендам, не абсолютным числам);
- судья годится для сравнения версий (A/B), не для приёмки отчёта заказчику.

## 5.4. Регламент выпуска изменений

Любое изменение (промпт, шаблон, индекс, модель, адаптер) проходит:

1. быстрый регрессионный прогон (10–15 писем, автометрики) — в CI;
2. полный прогон по золотому набору — перед выкаткой;
3. сравнение с текущим продуктивом; выкатка, только если ни одна метрика не
   упала более чем на порог;
4. запись в журнал изменений: что поменяли, что стало с метриками.

Автометрики полезно оформить обычными юнит-тестами — тогда «сломал промпт»
видно сразу, а не через месяц по жалобам.

## 5.5. Обязательный мониторинг в проде

- доля отчётов, заблокированных верификатором (рост = что-то сломалось);
- доля секций, перегенерированных инженером вручную (по секциям — видно, какой
  шаблон плох);
- частота `[ТРЕБУЕТ ПРОВЕРКИ]` по типам фактов (видно, каких измерений не
  хватает в слое 1);
- средний edit distance по неделям — главный график для руководства.

Данные для этого уже лежат в базе: замечания верификатора — в
`reports.issues_json`, отметка о перегенерации — в `report_sections.regenerated`,
расстояние правки — в `edit_pairs.edit_distance` (сводка по всем парам и по
секциям — `reportgen stats`). Разбивки по неделям система не строит: это
запрос к базе или выгрузка в таблицу.
