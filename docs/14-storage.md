# 14. SQLite или PostgreSQL

Короткий ответ: **для вашей установки SQLite лучше, и переезд на PostgreSQL
сейчас ухудшит систему, а не улучшит**. Но у SQLite есть один настоящий предел,
и упрётесь вы в него не там, где ожидаете — не в реляционной части, а в
векторном поиске. Ниже — числа, по которым можно решать самостоятельно.

## 14.1. Что сейчас

Одна база SQLite в режиме WAL: пользователи, кейсы, отчёты по версиям и
секциям, библиотека с полнотекстовым индексом FTS5, векторы, пары «черновик —
финал» для дообучения, разговоры с помощником, журнал действий.

Соединение — своё на каждый поток веб-сервера, записи сериализуются замком.
Это не мелочь: до исправления все запросы шли через одно общее соединение, и
при шести одновременных потоках из 240 записей сохранялось 46 — транзакции
разных запросов закрывали друг друга. Регрессионный тест на это есть
(`tests/test_store.py::ConcurrencyTests`).

## 14.2. Что SQLite реально выдерживает

| Величина | Ваш ожидаемый масштаб | Предел SQLite | Запас |
|---|---|---|---|
| Одновременных пользователей | 3–10 | сотни на чтение, писатель по очереди | ×30 |
| Записей в секунду | единицы (сохранение секции, сообщение в чат) | тысячи мелких транзакций в секунду на NVMe | ×100 |
| Кейсов и отчётов | сотни в год | миллионы строк | ×1000 |
| Размер базы | единицы ГБ | 281 ТБ теоретически, десятки ГБ практически | велик |
| Чанков библиотеки | 50–300 тысяч | миллионы (FTS5 справляется) | ×10 |
| Поиск по FTS5 | < 50 мс на 300 тысячах чанков | — | — |

Записи в этой системе крошечные: сохранить секцию — это несколько килобайт,
сообщение в чат — меньше. Транзакция занимает доли миллисекунды. Десять
инженеров, сохраняющих правку каждые несколько секунд, дают нагрузку, которую
SQLite не заметит.

## 14.3. Настоящий предел: векторный поиск

Вот где цифры перестают быть комфортными.

Плотный поиск сейчас — полный перебор: косинус между вектором запроса и всеми
векторами чанков.

| Чанков | Объём векторов (1024 измерения, float32) | Время одного поиска |
|---|---|---|
| 20 000 | 80 МБ | ~20 мс |
| 100 000 | 400 МБ | ~100 мс |
| 300 000 | 1.2 ГБ | ~0.4 с |
| 1 000 000 | 4 ГБ | 1.5–3 с и заметный расход памяти |

До 100 тысяч чанков (это примерно 30–50 тысяч страниц технической литературы)
перебор незаметен. Дальше нужен приближённый индекс.

**И вот главное: PostgreSQL эту задачу решает не лучше.** Варианты:

| Решение | Что даёт | Чего стоит |
|---|---|---|
| **faiss или hnswlib рядом с SQLite** | Поиск за единицы миллисекунд на миллионах векторов | Один файл индекса, ~50 строк кода в `search.py`, никакой новой инфраструктуры |
| **PostgreSQL + pgvector с HNSW** | То же самое | Плюс целая СУБД: установка, настройка, резервирование, мониторинг, обновления |

То есть момент, когда «SQLite перестанет тянуть», — это момент добавить faiss,
а не менять СУБД. Заложите это в план: строка в `search.py`, а не проект.

## 14.4. Когда PostgreSQL действительно нужен

Не «когда данных много», а когда появляется одно из этого:

| Условие | Почему SQLite не подходит |
|---|---|
| **Два и более сервера приложения** (отказоустойчивость, балансировка) | Файловая база не разделяется между машинами; сетевая ФС для SQLite — известный способ повредить базу |
| **К данным нужен доступ из других систем компании** (тикет-система, 1С, BI-отчётность) | Нужен сетевой доступ, роли, представления — это и есть работа СУБД |
| **Требование политики**: централизованная СУБД с резервированием, репликацией и аудитом силами отдела ИТ | Организационное, а не техническое |
| **Разграничение доступа на уровне строк** средствами СУБД | В SQLite нет row-level security; сейчас доступ проверяется в приложении |
| **Устойчиво больше ~50 записей в секунду** | Писатель в SQLite один; очередь начнёт расти |
| **Онлайн-репликация в резервный ЦОД** | Средствами SQLite не делается |

Из этого списка для вас реалистичны два пункта: доступ из тикет-системы и
требование ИТ-политики. Оба — организационные и заранее известные. Если такое
требование уже есть — переезжайте сразу, не накопив данных.

## 14.5. Во что обойдётся переезд

Весь SQL системы собран в одном файле — `src/reportgen/store/repo.py`. Слои
выше (сервис отчётов, помощник, веб, CLI) SQL не пишут вообще. Это и есть шов
для миграции.

| Работа | Оценка |
|---|---|
| Схема: `schema.sql` → DDL PostgreSQL (типы, `SERIAL`/`IDENTITY`, `ON CONFLICT`) | 0.5 дня |
| Полнотекстовый поиск: FTS5 → `tsvector` + GIN (русская морфология там своя, стеммер из `retrieval.py` останется как есть) | 1 день |
| Векторы: BLOB → `pgvector` + HNSW | 0.5 дня |
| Репозитории: параметры `?` → `%s`, курсоры, пул соединений | 1 день |
| Прогон 145 тестов хранилища на новой базе, правка расхождений | 1–2 дня |
| Развёртывание: контейнер, резервирование, мониторинг, перенос данных | 1–2 дня |
| **Итого** | **5–7 рабочих дней** |

Эти пять-семь дней никуда не денутся, но их можно потратить тогда, когда
появится причина, а не заранее.

## 14.6. Что уже сделано, чтобы переезд остался дешёвым

- Весь SQL — в репозиториях; ни один слой выше не знает, что база это SQLite.
- Схема в отдельном файле с механизмом добавления колонок
  (`store/db.py`, `COLUMN_MIGRATIONS`) — обновление базы вместе с кодом.
- 145 тестов хранилища работают через публичный интерфейс репозиториев, а не
  через SQL: они же станут приёмочными тестами новой базы.
- Идентификаторы — целые из последовательности, без завязки на особенности
  SQLite; временные метки — строки ISO-8601 в UTC.

Чего делать **не** нужно: вводить ORM «на будущее». SQLAlchemy добавит слой,
который придётся понимать всем, кто будет сопровождать систему, и сэкономит
из перечисленных семи дней примерно один.

## 14.7. Рекомендация

1. **Сейчас** — SQLite. Один файл, который можно скопировать на флешку и
   восстановить целиком; ноль эксплуатации; ровно то, что нужно отделу.
2. **Когда чанков станет больше ~150 тысяч** — добавить faiss или hnswlib для
   плотного поиска. СУБД при этом не меняется.
3. **Когда появится второй сервер приложения или доступ из других систем
   компании** — переезжать на PostgreSQL, заложив неделю работы.
4. **Резервное копирование** одинаково обязательно в обоих случаях: невосполнимы
   не индексы, а кейсы, отчёты и накопленные правки инженеров (док. 07, 11).
