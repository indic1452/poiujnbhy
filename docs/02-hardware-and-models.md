## 2.1. Арифметика VRAM (считайте сами, это 3 формулы)

**Веса:**

```
VRAM_весов (ГБ) ≈ N_параметров(млрд) × байт_на_параметр
    FP16/BF16 : 2.0    (эталон качества)
    FP8/INT8  : 1.0    (потери почти незаметны)
    4-bit     : ~0.55  (AWQ/GPTQ/Q4_K_M, с учётом накладных)
```

**KV-кэш** (память под контекст, часто её недооценивают):

```
KV (ГБ) ≈ 2 × L × H_kv × d_head × T × байт / 2^30
    L      — число слоёв
    H_kv   — число KV-голов (GQA сильно уменьшает: часто 8 вместо 64)
    d_head — размер головы (обычно 128)
    T      — длина контекста в токенах
    байт   — 2 при FP16-кэше, 1 при FP8-кэше
```

Пример: модель 32B, L=64, H_kv=8, d_head=128, контекст 32k, FP16-кэш →
2 × 64 × 8 × 128 × 32768 × 2 / 2^30 ≈ **8 ГБ** на одну параллельную сессию.
Это к 18 ГБ весов в 4 бита. Отсюда 32 ГБ карта — впритык, 48 ГБ — комфортно.

**Итого:** `VRAM ≈ веса + KV × одновременных_сессий + 2–4 ГБ (активации, фрагментация)`

## 2.2. Ваша текущая конфигурация: RTX 4080 + Xeon E5-2680 + 64 ГБ

Вводные: **RTX 4080 — 16 ГБ GDDR6X** (~716 ГБ/с, Ada, есть FP8), **Xeon
E5-2680** (по частоте 2.4 ГГц — судя по всему v4, Broadwell, 14 ядер, AVX2 без
AVX-512, PCIe 3.0, четырёхканальная DDR4-2400 ≈ 60–70 ГБ/с реальных),
**64 ГБ ОЗУ**.

Короткий вывод: **этого достаточно, чтобы пройти этапы 0–3 дорожной карты и
получить рабочие черновики отчётов.** Ограничение одно и понятное — 16 ГБ
VRAM. Апгрейд понадобится не «чтобы заработало», а «чтобы стало лучше», и
решать про него нужно после этапа 4, по замерам.

### Что реально влезает

Расчёт по формулам 2.1, с KV-кэшем в Q8 и контекстом 16k (для посекционной
генерации из док. 04 этого хватает с запасом):

| Модель | Квант | Веса | Куда влезает | Ожидаемая скорость | Роль |
|---|---|---|---|---|---|
| MoE ~20B, ~3–4B активных (напр. GPT-OSS-20B, MXFP4) | native 4-bit | ~12–13 ГБ | **целиком в VRAM** | 60–100 ток/с | **основной кандидат №1** |
| MoE ~30B, ~3B активных (напр. Qwen3-30B-A3B) | Q4_K_M | ~18 ГБ | 13–14 ГБ в VRAM + эксперты в ОЗУ | 15–30 ток/с | **основной кандидат №2, качество выше** |
| Dense 12–14B (Qwen3-14B, Mistral-Nemo-12B, Vikhr-Nemo-12B) | Q5_K_M | ~9–10 ГБ | **целиком в VRAM**, контекст до 32k | 35–55 ток/с | рабочая лошадка, кандидат для дообучения |
| Dense 24B (Mistral-Small-3.x) | Q4_K_M | ~14 ГБ | целиком, но контекст ≤ 8–12k | 25–35 ток/с | если нужен dense получше |
| Dense 32B (Qwen3-32B) | Q4_K_M | ~19 ГБ | частично в ОЗУ | 4–8 ток/с | только ночной пакетный прогон и «судья» |
| Dense 70B | любой | 40+ ГБ | нет | ~1–2 ток/с | не рассматривать |

Ключевое наблюдение: на 16 ГБ **MoE-модели дают качество заметно выше своего
класса**, потому что в оперативную память уходят редко используемые эксперты,
а считается всего 3–4 млрд активных параметров. Ровно ваш случай: много
дешёвой DDR4 и мало VRAM. Начните с MoE ~20B целиком в VRAM, затем сравните с
MoE ~30B с выгрузкой — на своём эвал-наборе (док. 05), а не по бенчмаркам.

Чего **не** хватит: 120B-класса MoE (в Q4 это ~60–65 ГБ — не помещается в
64 ГБ ОЗУ вместе с системой) и любых dense-моделей от 70B.

### Движок: здесь именно llama.cpp, не vLLM

Для этой машины **llama.cpp / Ollama — правильный выбор**, а не vLLM:

- vLLM плохо работает с частичной выгрузкой в ОЗУ, а вам она нужна;
- llama.cpp умеет держать в VRAM attention-слои и общие веса, а экспертов MoE
  класть в ОЗУ (`--n-cpu-moe` / `-ot`) — это даёт те самые 15–30 ток/с на 30B;
- квантованный KV-кэш (`--cache-type-k q8_0 --cache-type-v q8_0`) экономит
  половину памяти под контекст;
- работает на Broadwell без AVX-512 без проблем.

Ориентировочный запуск сервера (подставьте свою модель):

```bash
./llama-server \
  -m models/model-Q4_K_M.gguf \
  --host 127.0.0.1 --port 8000 \
  -c 32768 \                  # общий контекст на все слоты
  -ngl 999 \                  # все слои на GPU, что не влезет — уйдёт в ОЗУ
  --n-cpu-moe 12 \            # столько слоёв экспертов держать на CPU (подберите)
  --cache-type-k q8_0 --cache-type-v q8_0 \
  --flash-attn \
  -t 14 \                     # по числу физических ядер
  --parallel 2                # 2 одновременных слота
```

Про `-c 32768`. Это общий контекст, при `--parallel 2` на один разговор
приходится 16384 токена. Столько нужно помощнику: он кладёт в промпт до
26 000 знаков материала из библиотеки (`assistant_context_chars`) и оставляет
4000 токенов на ответ (`assistant_max_tokens`). При 8192 на слот промпт не
помещается, и llama.cpp обрезает его молча — выбрасывает начало вместе
с системной инструкцией. Внешне это выглядит так, будто модель «поглупела»:
она перестаёт ставить ссылки `[S1]` на источники и начинает отвечать по
памяти. Ошибки в логах при этом нет.

KV-кэш при `--cache-type q8_0` занимает около 85 КБ на токен, то есть
32768 токенов — примерно 2,8 ГБ видеопамяти. Вместе с моделью Qwen3-14B
Q5_K_M (10,5 ГБ) и рабочими буферами выходит около 14,4 из 16 ГБ. Если
сервер не поднимается, снижайте контекст ступенями — 24576, затем 16384 —
и вместе с ним уменьшайте `assistant_context_chars` (18000, затем 11000).

API совместим с OpenAI, поэтому каркас из этого репозитория работает как есть:
`--llm openai --base-url http://127.0.0.1:8000/v1`.

Подбор `--n-cpu-moe` — единственный параметр, который стоит покрутить: берите
максимальное число слоёв на GPU, при котором VRAM занята на ~14.5 из 16 ГБ.

### Эмбеддер и реранкер

Одновременно с LLM в 16 ГБ они не поместятся комфортно. Схема:

- **Построение индекса** (разовая тяжёлая операция): выгружаете LLM, гоняете
  `bge-m3` на GPU — сотня тысяч чанков индексируется за десятки минут.
- **В работе**: эмбеддер и реранкер держите на CPU (14 ядер справятся: один
  запрос — это 1 эмбеддинг + реранк 50 кандидатов, доли секунды), LLM — на GPU.
  Либо второй маленький процесс llama.cpp с GGUF-версией bge-m3 на 1–2 ГБ VRAM.

### Дообучение на этом железе

- QLoRA для моделей **до 14B** — реально: 4-bit база + LoRA r=16, длина 2048–4096,
  batch 1 + накопление градиента, gradient checkpointing, Unsloth. Прогон на
  3 тыс. примеров — ночь-полторы.
- 24–32B — на 16 ГБ не поместится даже в QLoRA с приемлемой длиной. Варианты:
  арендовать GPU на несколько часов в изолированном порядке (но тогда наружу
  уходят обучающие данные — см. док. 07, скорее всего нельзя), либо ждать
  апгрейда, либо дообучать 14B и использовать её как «стилиста» поверх
  большой модели-аналитика.
- Практичный план: **до апгрейда живите на RAG + промптах** (док. 3.4 прямо
  говорит, что это правильный порядок), дообучение — на этапе 5.

### Узкие места этой машины, кроме VRAM

| Что | Влияние | Что делать |
|---|---|---|
| DDR4-2400, 4 канала | Определяет скорость MoE-выгрузки: скорость генерации ≈ пропускная способность ОЗУ / объём активных весов в ОЗУ | Проверьте, что все 4 канала заняты (4 или 8 планок, а не 2) — это буквально ×2 к скорости выгрузки |
| 64 ГБ ОЗУ | Потолок по размеру MoE; индексация большого корпуса | +64 ГБ RDIMM DDR4-2400 стоит недорого — **самый дешёвый апгрейд с реальным эффектом** |
| PCIe 3.0 | Загрузка модели, обмен при выгрузке | Терпимо; на скорость генерации влияет слабо |
| Broadwell, старая архитектура | Медленный препроцессинг PDF/OCR и CPU-эмбеддинги | Индексацию делать на GPU пакетно |
| Двухсокетность (если есть) | NUMA роняет llama.cpp в 1.5–2 раза | Привязать процесс к одному сокету (`numactl --cpunodebind=0 --membind=0`) |
| Диск | Модели по 10–20 ГБ, корпус, индексы | NVMe на 2 ТБ (при отсутствии M.2 — через PCIe-адаптер) |

### Порядок апгрейда, когда дойдёт до него

1. **+64 ГБ ОЗУ** (десятки тысяч ₽) — открывает MoE покрупнее с выгрузкой.
2. **NVMe 2 ТБ** — если ещё нет.
3. **GPU 24–32 ГБ**: б/у RTX 3090 24 ГБ — лучшее соотношение цена/VRAM (можно
   поставить второй картой к 4080 и объединить память в llama.cpp); новая
   RTX 5090 32 ГБ — если нужен запас и гарантия. Только после этого имеет смысл
   говорить про dense 32B в продуктиве и QLoRA на 32B.
4. Серверная карта 48+ ГБ — не раньше, чем поток отчётов это оправдает.

Отдельно: **этап 1 дорожной карты (автоанализ дампов и сигналов) вообще не
использует GPU**. Пока идёт его разработка — а это 4–8 недель, самая
трудоёмкая часть проекта — имеющегося железа хватает с избытком.

## 2.3. Три конфигурации под бюджет

### Вариант A. «Пилот на рабочей станции» — 1 GPU 24–32 ГБ

- 1× RTX 4090 24 ГБ / RTX 5090 32 ГБ (или RTX 4000/5000 Ada для тихого офиса),
  64–128 ГБ RAM, NVMe 2 ТБ.
- Модель: dense 14–32B в 4 бита, контекст 24–32k, 1–2 сессии.
- Скорость: ~20–45 ток/с генерации — секция отчёта за 20–60 с, полный отчёт
  на 30 страниц за 10–25 минут. Для пакетного ночного прогона этого хватает.
- Годится для: пилота, RAG, генерации черновиков, LoRA-дообучения моделей до 14B.
- Порядок цены: 400–700 тыс. ₽ за станцию целиком.

Ваш сервер (раздел 2.2) — на ступеньку ниже этого варианта, но того же класса:
разница в 8–16 ГБ VRAM, которая закрывается выбором MoE-модели.

**С такой конфигурации нужно начинать.** Реальные ограничения вы увидите только на своих
данных, и покупать сразу сервер за 10 млн — способ купить не то.

### Вариант B. «Рабочий контур отдела» — 48–96 ГБ VRAM

- 1–2× RTX 6000 Ada / RTX PRO 6000 (48–96 ГБ) или 1× H100/H200 80–141 ГБ,
  256 ГБ RAM, NVMe RAID.
- Модель: dense 70B в 4–8 бит **или** MoE 100–130B в 4 бита (MoE выгоднее:
  при 120B параметров активны ~5B, скорость как у маленькой модели).
- Контекст 64–128k, 4–8 параллельных сессий, реранкер и эмбеддер на той же карте.
- Годится для: продуктива на отдел, QLoRA-дообучения 32–70B.
- Порядок цены: 1.5–4 млн ₽.

### Вариант C. «Тяжёлый контур» — 4–8 GPU

Нужен, только если появится (а) поток десятки отчётов в день, (б) требование
контекста 200k+ на документ целиком, (в) полноценный SFT крупных моделей.
Реалистично — не раньше года эксплуатации. Не закладывайте в первый бюджет.

### Вариант D. Без GPU (если закупка затянулась)

MoE-модели в GGUF на CPU с большим объёмом RAM (Epyc/Xeon, 256+ ГБ, llama.cpp)
дают 5–15 ток/с. Ночная пакетная генерация отчётов — реально. Интерактив — нет.
Как временное решение на этапе, пока вы отлаживаете слой автоанализа
(который GPU вообще не требует), это нормально.

## 2.4. Выбор LLM

Критерии именно под вашу задачу, по важности:

1. **Русский технический язык** — большинство западных моделей пишут по-русски
   грамматически верно, но «переводно». Проверяйте на своих отчётах вслепую.
2. **Следование инструкциям и структуре** — важнее «эрудиции»: факты вы даёте
   сами через RAG.
3. **Работа с длинным контекстом** без деградации в середине (тест
   «needle-in-haystack» на ваших документах, а не заявленное окно).
4. **Лицензия** — коммерческое использование, отчёты идут по назначению.
5. **Возможность дообучения** (открытые веса, поддержка LoRA в популярных фреймворках).

Что смотреть (семейства, актуальные на момент написания):

| Класс | Кандидаты | Комментарий |
|---|---|---|
| 7–14B | Qwen3-8/14B, Mistral-Nemo-12B, Gemma-3-12B, Vikhr-Nemo-12B | Только черновики и вспомогательные задачи (классификация, извлечение) |
| 24–32B | Qwen3-32B, Mistral-Small-3.x-24B, Gemma-3-27B, T-pro-it (рус. адаптация Qwen) | **Рабочая точка для варианта A.** Лучший баланс качество/VRAM |
| MoE 30–130B | Qwen3-30B-A3B, GPT-OSS-20B/120B (Apache-2.0), Llama-4-Scout | Скорость малой модели при качестве большой; отлично для варианта B |
| 70B+ dense | Llama-3.3-70B, Qwen3-72B-класс | Заметно лучше на сложных выводах, дороже по железу |

Отдельно про русскоязычные адаптации (RuadaptQwen, T-lite/T-pro, Vikhr): они
обычно выигрывают в естественности русского текста и в токенизации (меньше
токенов на тот же текст → дешевле контекст), но могут отставать в
рассуждениях. Прогоните обе ветки на своём эвал-наборе (док. 05) — это 2 дня
работы, которые окупятся.

**Reasoning-модели** (с длинной цепочкой рассуждений) полезны на этапе
интерпретации находок, но дороги по токенам и склонны «переусложнять» текст
отчёта. Практичная схема: reasoning-модель — для анализа и выводов, обычная
instruct — для написания секций.

## 2.5. Модели для поиска (RAG)

Эмбеддер важнее LLM для итогового качества: не найдёте нужную страницу
даташита — не поможет никакая модель.

- **Эмбеддинги:** `bge-m3` (мультиязычный, до 8k, даёт сразу плотные + разреженные
  векторы), `multilingual-e5-large`, `jina-embeddings-v3`, из русских — `FRIDA`,
  `USER-bge-m3`. Требуют ~2–4 ГБ VRAM, могут жить на CPU.
- **Реранкер (обязателен):** `bge-reranker-v2-m3` или аналог. Схема: BM25 + плотный
  поиск дают 50–100 кандидатов → реранкер оставляет 5–10. Это единственный
  самый выгодный по соотношению «усилие/качество» компонент всей системы.
- **Векторная БД:** до ~1 млн чанков достаточно `faiss` + SQLite/Postgres для
  метаданных; `Qdrant` — если нужна фильтрация по метаданным и обновления на лету.
  `pgvector`, если Postgres уже есть в контуре.

## 2.6. Разбор PDF (это будет ваша главная боль)

Техническая литература — это сканы, формулы, таблицы, схемы, двухколоночная
вёрстка. Плохой парсинг PDF убивает RAG надёжнее, чем плохая модель.

- **Текстовые PDF:** `PyMuPDF` (быстро), `docling` или `marker` (структура,
  заголовки, таблицы → Markdown).
- **Сканы:** OCR `PaddleOCR` / `surya` / `tesseract` (с `rus+eng`), для формул —
  специализированные модели распознавания LaTeX.
- **Таблицы:** извлекать отдельно и хранить как Markdown/CSV в чанке целиком —
  разрезанная пополам таблица бесполезна.
- **Схемы и графики:** прогоняйте через VLM (визуальную модель) для генерации
  текстового описания, индексируйте описание, в отчёт вставляйте картинку.

Заложите на это 2–3 недели работы одного человека. Автоматика даст 80%,
остальное — выборочная ручная проверка ключевых 50–100 документов.

## 2.7. Движок инференса

| Движок | Когда брать |
|---|---|
| **vLLM** | Основной выбор для GPU-продуктива: пропускная способность, батчинг, OpenAI-совместимый API, PagedAttention |
| **SGLang** | Альтернатива vLLM, сильна на структурированном выводе и префиксном кэше |
| **llama.cpp** | CPU / смешанный CPU-GPU, редкие квантизации, минимум зависимостей, оффлайн-контур |
| **Ollama** | Самый быстрый старт для пилота, под капотом llama.cpp; для продуктива — переезжайте на vLLM |
| **TensorRT-LLM** | Максимум скорости на NVIDIA ценой сложности сборки |

Все они дают OpenAI-совместимый HTTP API, поэтому код в этом репозитории
(`src/reportgen/llm.py`) работает с любым из них — меняется только `--base-url`.
Не привязывайтесь к конкретному движку в коде.

## 2.8. Структурированный вывод

Обязательно используйте **grammar-constrained decoding** (`guided_json` в vLLM,
GBNF в llama.cpp, `outlines`/`xgrammar`): промежуточные шаги конвейера
(классификация обращения, извлечение сущностей, план отчёта, самопроверка)
должны возвращать строгий JSON по схеме. Это убирает целый класс ошибок
парсинга и делает конвейер предсказуемым.
