# 06. Дорожная карта внедрения

Оценки в человеко-неделях для команды из 1 инженера-разработчика + участия
1–2 предметных экспертов на 20–30% времени. Железо для этапов 0–3 у вас уже
есть (RTX 4080, см. раздел 2.2 док. 02), закупка ничего не блокирует.

## Этап 0. Подготовка (2–3 недели)

| Задача | Результат |
|---|---|
| Инвентаризация данных (док. 3.1) | таблица источников с объёмами и правами |
| Выбор 2–3 самых частых типов обращений | приоритет автоматизации |
| Формализация шаблонов для них | `templates/outline_*.json`, написанные экспертом |
| Правовая проверка NDA и допустимости обработки | письменное решение |
| Развёртывание llama.cpp/Ollama + первая модель | «Hello» от локальной LLM |

**Критерий выхода:** есть шаблон отчёта в JSON и работающий локальный
инференс. Ни строчки продуктивного кода ещё не написано — и это правильно.

## Этап 1. Слой автоанализа (4–8 недель) — самый ценный

Здесь основная экономия времени и основное устранение человеческих ошибок,
причём **без всякого ИИ**.

| Задача | Результат |
|---|---|
| Разбор дампов: обёртки над tshark/scapy, конечные автоматы протоколов, диффы против эталона | детект «лишнего» в обмене автоматически |
| Обработка IQ: спектр, полоса, SNR/EVM, символьная скорость, сдвиг частоты, спуры | набор измерений с погрешностями |
| Демодуляторы под ваши типовые модуляции, BER/FER | измерения качества |
| Единая схема факт-пакета и её валидация | `facts.schema.json` |
| Автогенерация графиков (спектрограмма, созвездие, глазковая диаграмма) | PNG для отчёта |

**Критерий выхода:** для 3 типовых кейсов инженер запускает одну команду и
получает валидный факт-пакет с графиками, совпадающий с его ручным разбором.
Проверка на 20 исторических кейсах: расхождения разобраны.

> Если ресурсов мало — делайте **только этот этап**. Он окупается сам по себе,
> даже если генерация текста так и не будет внедрена.

## Этап 2. RAG-контур (3–4 недели)

| Задача | Результат |
|---|---|
| Конвейер PDF/DOCX → Markdown → чанки (док. 2.6, 3.3) | индексы A/B/C |
| Эмбеддер + BM25 + реранкер | гибридный поиск |
| Разметка 200–300 пар «запрос → нужный фрагмент» | эвал поиска |
| Глоссарий терминов | словарь канонизации |

**Критерий выхода:** `recall@10` ≥ 0.85 на размеченных парах. До этого числа
к генерации не переходить: плохой поиск невозможно компенсировать моделью.

## Этап 3. Генерация черновиков (3–4 недели)

| Задача | Результат |
|---|---|
| Посекционная генерация по шаблону | `pipeline.py` на реальной модели |
| Верификатор (числа, цитаты, структура) | блокирующие проверки |
| Сшивка, глоссарий, экспорт в DOCX по фирменному бланку | готовый файл |
| Золотой эвал-набор и автометрики (док. 05) | базовые цифры качества |

**Критерий выхода:** на 10 исторических кейсах черновик оценивается экспертом
на 3+ из 5 и требует не более ~60% времени от написания с нуля.

## Этап 4. Опытная эксплуатация (8–12 недель)

- Веб-интерфейс с тремя панелями (4.8), доступ 3–5 инженерам.
- Все реальные кейсы идут через систему **параллельно** обычному процессу;
  отчёт заказчику по-прежнему пишет человек, но начиная с черновика.
- Копятся пары «черновик → финал».
- Еженедельный разбор: что правили и почему; большинство находок чинится
  шаблоном или добавлением измерения в слой 1.

**Критерий выхода:** 30+ реальных кейсов, устойчивое снижение edit distance,
инженеры сами предпочитают начинать с черновика.

## Этап 5. Дообучение и масштабирование (4–6 недель, далее — постоянно)

- SFT/LoRA на обратно размеченных исторических отчётах (3.5) + правках (3.7).
- DPO на парах черновик/финал, когда их ≥ 500.
- Решение по апгрейду железа — уже на основе замеров, а не предположений.
- Расширение на остальные типы отчётов (шаблоны пишутся экспертами, код не меняется).

## Бюджет (порядок величин)

| Статья | Оценка |
|---|---|
| Железо | 0 ₽ на этапах 0–3 (используется имеющийся сервер); 400–900 тыс. ₽ на апгрейд GPU после этапа 4 |
| Разработка | 1 инженер на 8–9 месяцев |
| Время экспертов | 20–30% времени 1–2 инженеров, постоянно |
| ПО | 0 ₽ (всё в открытых лицензиях; проверьте лицензии конкретных моделей) |

## Риски и что с ними делать

| Риск | Вероятность | Митигация |
|---|---|---|
| Слой 1 недооценён: ручной разбор плохо формализуется | высокая | Начать с 2–3 самых типовых классов, остальное оставить человеку. Не пытаться покрыть всё |
| Плохой парсинг PDF рушит RAG | высокая | Бюджет 2–3 недели, ручная проверка топ-100 документов |
| Модель галлюцинирует числа | средняя | Архитектурный запрет: числа только из факт-пакета + блокирующий верификатор |
| Инженеры не примут систему | средняя | Внедрять как «черновик для вас», а не «замену вас». Дать кнопку перегенерации и правки фактов |
| Утечка данных заказчиков | низкая, ущерб высокий | Изолированный контур, анонимизация датасетов (док. 07) |
| Ожидание «оно само с завтрашнего дня» | высокая | Зафиксировать критерии выхода по этапам письменно и показывать метрики |

## Главный совет

Не начинайте с покупки большой модели и не начинайте с генерации текста.
Начинайте с того, чтобы **ручной анализ стал кодом**. Всё остальное —
надстройка над этим, и она соберётся быстро. Обратный порядок даёт красивую
демонстрацию через месяц и тупик через полгода.
