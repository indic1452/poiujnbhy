# 04. Конвейер отчёта: как получить документ на десятки страниц

## 4.1. Почему нельзя «одним промптом»

Соблазн: дать модели факт-пакет и сказать «напиши отчёт на 30 страниц».
Что произойдёт на практике:

- качество падает к концу документа (модель «устаёт»: повторы, вода, потеря нити);
- невозможно точечно перегенерировать один раздел, не тронув остальные;
- контекст забивается, растёт риск потери фактов из середины;
- нечего кэшировать, каждая итерация — полная перегенерация;
- нельзя параллелить.

Правильно — **план → секции → сшивка → редактура**, где каждая секция
генерируется отдельным вызовом с собственным узким контекстом. Это и быстрее,
и качественнее, и позволяет инженеру перегенерировать один раздел кнопкой.

## 4.2. Полный цикл

```
1. Классификация обращения       → тип отчёта (signal_issue / protocol_anomaly / …)
2. Выбор шаблона-плана           → templates/outline_*.json
3. Автоанализ (слой 1)           → факт-пакет
4. Проверка полноты фактов       → каких измерений не хватает для шаблона?
5. План документа                → секции + распределение фактов по секциям
6. Поиск контекста на секцию     → 5–10 чанков после реранка
7. Генерация секций              → параллельно, каждая со своим промптом
8. Сшивка                        → нумерация, ссылки, единый глоссарий
9. Редакторский проход           → устранение повторов, согласование выводов
10. Верификация                  → числа, цитаты, структура, противоречия
11. Экспорт                      → DOCX/PDF + приложения + графики
12. Правка инженером             → diff в датасет (док. 03)
```

Шаги 5–10 реализованы в каркасе (`src/reportgen/pipeline.py`, `verify.py`).

## 4.3. Шаблон-план (outline)

Машиночитаемый шаблон — сердце системы. Пример структуры одной секции:

```json
{
  "id": "measurement_conditions",
  "title": "Условия и методика измерений",
  "instruction": "Опиши условия и методику измерений по фактам ниже",
  "required_facts": ["center_frequency", "sample_rate", "capture_duration"],
  "optional_facts": ["antenna", "temperature"],
  "retrieval_queries": ["методика измерения занимаемой полосы"],
  "target_words": 250,
  "style": "нейтральный, прошедшее время, без оценочных суждений"
}
```

Что это даёт помимо генерации:

- `required_facts` работает **до** запуска модели: если измерения нет,
  система сразу говорит инженеру «для этого типа отчёта нужен ещё замер X» —
  это и есть механическое устранение человеческой забывчивости;
- `target_words` держит объём под контролем;
- секции с `severity`-зависимой логикой можно включать условно.

Заведите по шаблону на каждый устоявшийся тип обращения (см. 1.6). Шаблоны
пишутся не программистом, а старшим инженером — это формализация того, что
у него в голове.

## 4.4. Контекст одной секции

Собирается строго из пяти частей и ничего сверх:

1. **Системный промпт** — роль, жёсткие запреты (см. ниже), язык, стиль.
2. **Инструкция секции** из шаблона.
3. **Только относящиеся к секции факты** (по `required/optional_facts`), в виде
   компактной таблицы с единицами и погрешностями.
4. **Найденные фрагменты** (5–10 после реранка) с явными идентификаторами
   `[S1]`, `[S2]`, на которые модель обязана ссылаться.
5. **Краткое содержание уже написанных секций** (2–3 предложения на секцию) —
   чтобы не повторяться и не противоречить.

Жёсткие запреты в системном промпте, которые реально работают:

```
— Не используй ни одно число, которого нет в блоке ФАКТЫ. Округление
  запрещено: переноси значение как есть, вместе с единицей измерения.
— Любое утверждение о требованиях стандарта сопровождай ссылкой [S<N>]
  на предоставленный фрагмент. Нет фрагмента — нет утверждения.
— Если данных недостаточно, напиши "[ТРЕБУЕТ ПРОВЕРКИ: <чего не хватает>]"
  и продолжай. Не догадывайся.
— Не предлагай замену оборудования и не давай коммерческих оценок.
```

Последний пункт — пример защиты от того, что модель начнёт от лица компании
обещать заказчику лишнее.

## 4.5. Сшивка и редакторский проход

После генерации секций:

- **Нумерация и ссылки** — программно, не моделью (разделы, рисунки, таблицы,
  сноски). Модель ставит плейсхолдеры, код их разрешает.
- **Глоссарий** — программная замена по словарю синонимов на канонические
  термины («КБВ»/«SWR»/«КСВН» → один вариант).
- **Дедупликация** — если две секции содержат почти одинаковые абзацы
  (косинусная близость > 0.9), вторая сокращается со ссылкой на первую.
- **Согласованность выводов** — отдельный вызов модели: «Вот измерения и вот
  раздел «Выводы». Перечисли в JSON противоречия между ними». Reasoning-модель
  здесь окупается.
- **Резюме (executive summary)** пишется **последним**, по готовому документу,
  а не первым.

## 4.6. Верификация (слой 5)

Автоматические проверки перед показом инженеру:

| Проверка | Реализация | Действие при провале |
|---|---|---|
| Все числа из факт-пакета | регулярка + сверка с нормализованными значениями | блок, подсветка |
| Все `[S<N>]` существуют и релевантны | сверка с выданным контекстом | блок |
| Обязательные секции на месте, объём в допуске | сравнение с шаблоном | предупреждение |
| Нет запрещённых формулировок (гарантии, сроки, цены) | словарь + regex | блок |
| Термины по глоссарию | словарь | автозамена |
| Нет противоречий «выводы ↔ измерения» | LLM-судья | предупреждение |
| Нет остатков плейсхолдеров и `[ТРЕБУЕТ ПРОВЕРКИ]` | regex | предупреждение инженеру |

Реализация базовых проверок — `src/reportgen/verify.py`.

Важно: верификатор должен **блокировать экспорт**, а не просто предупреждать.
Предупреждения, которые можно проигнорировать, через месяц игнорируются всегда.

## 4.7. Производительность и кэширование

- Секции независимы → генерируйте параллельно (в vLLM — просто несколько
  запросов, батчинг сам).
- Общий префикс (системный промпт + факт-пакет) одинаков для всех секций →
  включайте prefix caching, экономит 30–60% времени.
- Перегенерация одной секции не трогает остальные — сделайте это кнопкой в
  интерфейсе, инженеры будут пользоваться постоянно.

## 4.8. Интерфейс для инженера

Минимально жизнеспособный: веб-страница с тремя панелями —

1. слева факт-пакет (редактируемый: инженер может поправить измерение или
   добавить своё наблюдение, и это сразу отражается в тексте);
2. по центру отчёт в Markdown-редакторе, секции сворачиваются, у каждой кнопки
   «перегенерировать», «сделать короче/подробнее», «добавить обоснование»;
3. справа источники: чанки, на которые ссылается текущая секция, с переходом
   на страницу PDF.

Плюс кнопка «Экспорт в DOCX» и «Утвердить» (последняя пишет пару
черновик/финал в датасет). Этого достаточно на первый год.
