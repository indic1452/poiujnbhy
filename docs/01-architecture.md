# 01. Архитектура

## 1.1. Постановка задачи и её честная декомпозиция

Исходное желание звучит как «обучить модель на литературе и отчётах, чтобы она
по ключевым словам сама писала отчёт». Внутри этого желания лежат три
принципиально разные задачи, и их нельзя решать одним инструментом:

| Задача | Природа | Чем решается | Допустима ли ошибка |
|---|---|---|---|
| A. Анализ артефакта (дамп, IQ-запись, лог) | детерминированные вычисления | DSP/парсеры/сигнатуры | нет |
| B. Интерпретация: «что эти числа значат» | экспертное знание | RAG + LLM + правила | ограниченно, с ссылкой на источник |
| C. Оформление документа | текст по шаблону | LLM | да, правится редактурой |

Языковая модель хорошо решает C, приемлемо — B при условии подачи ей
проверяемого контекста, и **плохо** решает A. У LLM нет FFT, нет конечного
автомата протокола и нет побитового разбора; всё это она будет имитировать.
При этом имитация выглядит убедительно: правдоподобный SNR = 14.7 дБ и
правдоподобный номер кадра. Именно такие ошибки страшнее человеческих, потому
что у них нет «запаха» ошибки — их не ловит беглая вычитка.

Вывод, на котором держится вся система: **числа рождаются в коде, текст
рождается в модели**. Модель не имеет доступа к сырому артефакту и физически
не может назвать число, которого нет в факт-пакете, — за этим следит
верификатор (слой 5).

## 1.2. Слои системы

```
┌─────────────────────────────────────────────────────────────────────┐
│ 0. Приём обращения                                                  │
│    вход: письмо/тикет + артефакты (pcap, IQ, csv, логи, фото)       │
│    выход: письмо с нормализованными файлами и метаданными           │
└───────────────────────────────┬─────────────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 1. Детерминированный анализ  (ваш существующий ручной труд → код)   │
│    • дампы: tshark/pyshark/scapy, конечные автоматы протоколов,     │
│      диффы против эталонной сессии, детект «лишнего» в стеке        │
│    • сигнал: numpy/scipy/GNU Radio — спектр, занимаемая полоса,     │
│      SNR/EVM/MER, созвездие, символьная скорость, частотный сдвиг,  │
│      джиттер, спуры, интермодуляция, маска передатчика              │
│    • демодуляция: готовые демодуляторы + BER/FER по известной       │
│      преамбуле                                                      │
│    выход: измерения + автоматические находки, всё с погрешностями   │
└───────────────────────────────┬─────────────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 2. Факт-пакет (JSON, версионируемый)  ← ЕДИНСТВЕННЫЙ ИСТОЧНИК ЧИСЕЛ │
│    measurements[]: имя, значение, единица, метод, погрешность,      │
│                    ссылка на артефакт и на строку/отсчёт            │
│    findings[]:     severity, заголовок, evidence[], ссылки на ГОСТ/ │
│                    рекомендации/даташит                             │
│    artifacts[], equipment, timeline, group_no, request              │
└───────────────────────────────┬─────────────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 3. Поиск знаний (RAG)                                               │
│    индекс A: техническая литература, стандарты, даташиты            │
│    индекс B: прошлые отчёты (по типу проблемы и оборудованию)       │
│    индекс C: внутренние регламенты, глоссарий, формулировки         │
│    гибрид BM25 + плотные векторы + реранкер                         │
└───────────────────────────────┬─────────────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 4. Генерация по секциям (локальная LLM)                             │
│    шаблон-план отчёта → для каждой секции свой промпт, свои факты,  │
│    свои найденные фрагменты → черновик секции → сшивка → редактура  │
└───────────────────────────────┬─────────────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 5. Верификация                                                      │
│    • каждое число текста ∈ факт-пакет (иначе — блок)                │
│    • каждое утверждение о стандарте имеет цитату из индекса         │
│    • структура соответствует шаблону, термины — глоссарию           │
│    • нет противоречий между секциями (заключение vs измерения)      │
└───────────────────────────────┬─────────────────────────────────────┘
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 6. Инженер в контуре: правит в редакторе, подтверждает              │

└───────────────────────────────┬─────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│ 7. Экспорт: DOCX/PDF по фирменному шаблону, графики из слоя 1,      │

└─────────────────────────────────────────────────────────────────────┘
```

Слой 0 — это раздел «Письма» в интерфейсе: входящее письмо и
подготовленный на него ответ, с входящим номером, датой, сроком, приоритетом
и исполнителем. В базе и в API письмо по-прежнему называется `case`: таблица
`cases`, маршруты `/api/cases`, поле факт-пакета `case_id`. Имя историческое;
переименование задело бы схему, данные, код и API разом, а на работающей
установке это дороже, чем один раз объяснить расхождение. Дальше в документах
письмом называется сущность, а `case` — то, как она названа в коде.

## 1.3. Почему RAG, а не «просто дообучить на отчётах»

Дообучение (fine-tuning) переносит в модель **стиль, структуру и жаргон**. Оно
почти не переносит факты: модель не начинает надёжно помнить, что в даташите
на конкретный трансивер маска передатчика такая-то. Факты нужно подавать в
контекст. Поэтому:

- **RAG отвечает за «что правда»** — литература, стандарты, даташиты, прошлые
  решения. Обновляется добавлением файла в индекс, без переобучения.
- **Fine-tuning отвечает за «как принято писать у нас»** — структура разделов,
  формулировки, степень категоричности выводов, оформление таблиц.
- **Факт-пакет отвечает за «какие числа в этом письме»**.

Эти три канала не взаимозаменяемы. Порядок внедрения: сначала RAG на базовой
модели (работает через 2–3 недели), дообучение — позже, когда накопится
размеченный корпус и станет понятно, чего именно не хватает (док. 03).

## 1.4. Ключевые инварианты

Их стоит зафиксировать как требования к системе и проверять тестами:

1. **Никаких чисел мимо факт-пакета.** Верификатор блокирует отчёт.
2. **Никаких утверждений о нормативах без цитаты.** Каждое «согласно…»
   сопровождается идентификатором фрагмента из индекса; фрагмент попадает в
   приложение отчёта.
3. **Воспроизводимость.** Отчёт = f(факт-пакет, версия индекса, версия модели,
   версия шаблона, seed). Первые четыре величины пишутся в служебный блок
   отчёта: `facts_digest`, `index_version`, `model`, `outline_version` (плюс
   дата сборки). Seed задан настройкой `llm_seed` (по умолчанию 0) и в блок не
   попадает — при разборе старого отчёта его берут из настроек установки.
   Через год можно повторить генерацию бит в бит.
4. **Отчёт не уходит без проверки начальником отдела.** Система — генератор
   черновика 90-процентной готовности, а не автопилот.
5. **Деградация безопасна.** Нет уверенного вывода — секция помечается
   `[ТРЕБУЕТ ПРОВЕРКИ: чего именно не хватает]`, а не заполняется догадкой.
   Пустое место инженер увидит, а красиво написанную неправду — не факт.
   Метку ставит модель по инструкции из `prompts.py`; верификатор находит
   каждую такую метку и выносит её в замечания к отчёту как предупреждение.

## 1.5. Где реально экономится время

Замер по типичному потоку (оценка, уточните на своих данных):

| Этап | Сейчас | С системой |
|---|---|---|
| Разбор артефакта | 2–6 ч ручной работы | 5–20 мин (автоанализ) + 30–60 мин проверки |
| Написание отчёта | 3–8 ч | 10 мин генерации + 40–90 мин редактуры |
| Согласование терминов/оформления | 0.5–2 ч | ~0 (шаблон и глоссарий) |

Основная экономия — не в LLM, а в **слое 1**: в кодификации того, что сейчас
инженеры делают руками. LLM даёт вторую половину выигрыша и, что важнее,
единообразие. Поэтому этап 1 дорожной карты — именно автоанализ, а не модель.

## 1.6. Типы отчётов = типы шаблонов

Не пытайтесь сделать один универсальный шаблон. Заведите отдельный план
(outline) на каждый повторяющийся класс обращений, например:

- `signal_issue` — проблема с сигналом/качеством канала;
- `protocol_anomaly` — аномалия в стеке протоколов, «лишнее» в обмене;
- `hw_failure` — отказ/деградация оборудования;
- `interop` — несовместимость оборудования разных вендоров;
- `acceptance` — приёмо-сдаточные измерения;
- `incident_postmortem` — разбор инцидента на объекте.

Шаблон описывает секции, их порядок, обязательные факты и целевой объём.
В поставке два готовых плана — `templates/outline_signal_issue.json` и
`templates/outline_protocol_anomaly.json`; остальные заводятся по их образцу.
Файл кладётся в каталог шаблонов с именем вида `outline_*.json`; тип отчёта
система берёт из поля `report_type` внутри файла, и он появляется в списке
типов при заведении письма.
Такая формализация сама по себе снижает число человеческих ошибок: «забыл
раздел про условия измерений» перестаёт быть возможным.
