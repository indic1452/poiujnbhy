# 13. Разнородная библиотека: направления, разметка, что дообучать

Документ отвечает на вопрос заказчика: у компании есть спутниковые и
радиорелейные линии, методические пособия по работе за оборудованием, стандарты
от модуляции до HDLC и прочих протоколов модели OSI — и всё это должно
обслуживать одну систему, которая пишет отчёты и отвечает на рабочие вопросы.

Продолжает док. [01](01-architecture.md), [03](03-data-and-training.md) и
[05](05-evaluation.md) и опирается на уже написанный код: `domains.py`,
`templates/domains.json`, `search.py`, `web/assistant.py`.

## 13.1. Короткий ответ

| Вопрос | Ответ | Где это в системе |
|---|---|---|
| Отдельная модель на спутник и отдельная на релейку? | Нет. Одна база, RAG на всю библиотеку, разные шаблоны-планы | 13.2 |
| Отдельный LoRA-адаптер на направление? | Только когда различается **стиль** отчёта и накоплено ≥ 300 пар секций этого типа | 13.2 |
| Как разложить библиотеку? | Два независимых поля: тип документа (5 значений) × направление (7 значений) | `corpus.DOC_TYPES`, `templates/domains.json` |
| «Уровень» — сигнала или OSI? | Фильтр по направлению + глоссарий с пометкой направления + расширение запроса | 13.4 |
| Пункты стандартов? | Чанк = пункт, номер в крошках, ответ обязан цитировать источник, не память | 13.5 |
| 200 отчётов по спутнику и 40 по релейке? | Один обучающий набор, ограничение сверху на частое направление, эвал с разбивкой | 13.6 |
| Добавили тропосферную связь? | Строка в `templates/domains.json`, документы, шаблон, эвал. Модель не трогать | 13.8 |

## 13.2. Одна модель, а не семь

### Что чем переносится

Три канала знания не взаимозаменяемы (док. 01, 1.3). На ваших данных это
выглядит так:

| Канал | Что несёт | Пример из вашей библиотеки | Как обновляется |
|---|---|---|---|
| RAG | факты и нормы | дождевое затухание в Ku, состав поля Control в HDLC, маска передатчика из даташита | положить файл в библиотеку |
| Шаблон-план | структура отчёта | приёмо-сдаточные измерения по РРЛ ≠ разбор аномалии протокола | `templates/outline_*.json` |
| LoRA-адаптер | стиль и тон | степень категоричности выводов, оформление таблиц | ночной прогон, ≥ 300 пар |
| Факт-пакет | числа конкретного кейса | EVM 12,3 %, число ошибок CRC | слой автоанализа |

Различие между спутником и релейкой — **фактическое**: другая физика, другие
нормы, другие термины. Это канал RAG. Стиль отчёта у обоих один: тот же отдел,
тот же бланк, тот же глоссарий, те же требования к формулировкам. Дообучать
модель ради фактов — значит платить за то, что дешевле подать в контекст, и
получать факты, которые нельзя обновить и нельзя проверить по ссылке.

### Арифметика семи моделей

| Статья | Одна модель | Семь моделей |
|---|---|---|
| VRAM (RTX 4080, 16 ГБ) | одна модель в памяти | вторая не влезает; переключение = перезагрузка 8–20 ГБ, десятки секунд на запрос |
| Обучающие данные | 300–800 пар секций даёт сдвиг стиля (док. 03, 3.6) | 300 × 7 = 2100 отчётов оценки 4–5, после дедупликации ещё меньше |
| Эвал | один золотой набор 40–60 кейсов | семь наборов, семь порогов, семь регрессов на каждое изменение промпта |
| Сопровождение | одна карточка адаптера | семь карточек, семь дат, семь ответов на вопрос «почему v3 лучше v2» |
| Кросс-вопросы | «почему на релейке растёт CRC при замираниях» отвечается сразу | вопрос попадает между моделями |

Второй строки достаточно, чтобы закрыть тему: 2100 отчётов оценки 4–5 нет ни у
кого, а по редким направлениям их у вас десятки. Адаптер, обученный на 140
парах, даёт не «специалиста по релейкам», а модель, дословно воспроизводящую
обороты двадцати конкретных отчётов. Семь **адаптеров** поверх одной базы
физически дёшевы (LoRA r=16 на 14B — 40–120 МБ) и переключаются на лету; дорого
не хранение, а данные, эвал и сопровождение — строки 2–4 таблицы.

### Когда шаблона достаточно, а когда нужен адаптер

| Ситуация | Решение |
|---|---|
| Различается состав и порядок разделов | шаблон-план (`templates/outline_*.json`) |
| Различается терминология | глоссарий + `retrieval_queries` секции в терминах направления |
| Различается набор обязательных измерений | `required_facts` шаблона, `coverage` покажет нехватку |
| Заказчик требует свою форму отчёта | шаблон + `instruction` секции |
| Отчёты по направлению пишет другой отдел с другой школой изложения, правки инженеров систематически не сходятся с общей моделью | **отдельный адаптер** |
| Пар «черновик → финал» по направлению < 300 | адаптер невозможен, только шаблон |

Численный критерий для второго адаптера: на подмножестве эвал-набора по этому
направлению общий адаптер даёт средний edit distance выше, чем по набору в
целом, на 0.10 и более, и это воспроизводится на ≥ 15 кейсах. Меньшая разница —
шум, лечится шаблоном и промптом.

## 13.3. Два измерения: тип документа × направление

### Почему именно два

Тип документа отвечает на вопрос **«как этому верить и как это цитировать»**:
стандарт — норма, даташит — параметр конкретной железки, прошлый отчёт —
формулировка и прецедент, регламент — как у нас принято. Направление отвечает
на вопрос **«про что это»**. Вопросы независимы: стандарты есть в каждом
направлении, в каждом направлении есть все пять типов.

| Направление | literature | standards | datasheets | reports | regulations |
|---|---|---|---|---|---|
| Спутниковая связь | том по спутниковым линиям | ITU-R P.618, дождевое затухание | руководство на VSAT-модем | отчёты по деградации Ku-линии | регламент приёмки земной станции |
| Радиорелейная связь | расчёт пролётов, зоны Френеля | нормы на РРЛ | паспорт на ODU/IDU | отчёты по замираниям на пролёте | порядок ПСИ на РРЛ |
| Протоколы и стек OSI | учебник по стеку | описание HDLC, кадр Ethernet | описание интерфейсов платы | разборы аномалий обмена | правила описания дампов в отчёте |
| Модуляция | обработка сигналов, созвездия | требования к EVM/маске | параметры модема | отчёты по качеству модуляции | — |
| Измерения и методики | методики измерений | методики по ГОСТ | руководство на анализатор спектра | протоколы измерений | внутренние методики |
| Оборудование | пособия по эксплуатации | — | даташиты | отчёты по отказам | регламент ТО |
| Нормативы (сквозные) | — | сквозные РД и приказы | — | — | внутренние регламенты оформления |

Одно дерево каталогов не работает по трём причинам:

1. Документ пришлось бы класть ровно в одно место. Методичка по релейному
   модему с главой про HDLC — это «релейка» или «протоколы»? Любой ответ
   ломает один из двух видов поиска.
2. Нужны оба среза сразу: «покажи все стандарты» (аудит нормативной базы) и
   «покажи всё по релейке» (подготовка к обращению). Дерево даёт только один.
3. Третий срез (вендор, модель оборудования, год) множил бы каталоги
   комбинаторно.

### Как это устроено в коде

- **Тип** определяется каталогом верхнего уровня библиотеки: `library/standards/…`,
  `library/reports/…` (`corpus.DOC_TYPES`, разбор в `ingest/pipeline.py`).
  Тип неизменен для документа и меняется переносом файла.
- **Направление** — отдельное поле документа и каждого чанка. Ставится при
  загрузке (`POST /api/library/upload`, поле формы `domain`), либо
  автоматически (`DomainRegistry.classify`), либо руками потом
  (`PUT /api/library/{doc_id}/domain`). `DocumentRepo.set_domain` обновляет и
  документ, и его чанки, поэтому переразметка **не требует ни переконвертации,
  ни перестроения векторов** — только сброс кэша поисковика, что API делает сам.
- Список направлений — данные, а не код: `templates/domains.json`
  перечитывается по времени модификации файла (`domains.registry`).

### Правило для направления «нормативы»

Это самое частое место, где разметка портится. `doc_type=standards` — это **вид
документа**. `domain=regulation` — это **предмет**: сквозные РД, приказы,
внутренние регламенты оформления, то есть нормативные документы вне конкретной
техники.

> ГОСТ на радиорелейные линии — это `standards` × `microwave`, а не
> `standards` × `regulation`. Иначе фильтр «релейка» перестанет находить
> норму, по которой пишется вывод отчёта.

Классификатор этого различия не знает: ключевые слова направления `regulation`
(`гост`, `стандарт`, `норм`, `требовани к`) встречаются в любом стандарте по
любому направлению. Поэтому именно стандарты размечаются руками. Их у вас
десятки, а не тысячи — это половина дня работы, окупается сразу.

### Что не надо превращать в третье измерение

Вендор, модель оборудования, год, номер редакции, гриф — это метаданные чанка
(`Chunk.meta`, фильтр `meta_filter` в обоих поисковиках). Они нужны точечно
(«даташит именно этого вендора»), а не для группировки библиотеки.

### Документ, покрывающий два направления

Направление ставится по документу целиком, по основному предмету. Глава про
HDLC внутри методички по релейному модему найдётся лексикой и по «хлебным
крошкам» (`Chunk.indexed_text` включает путь заголовков). Резать документ на
файлы стоит только если это фактически сборник (подшивка стандартов, комплект
руководств) — и тогда до индексации.

## 13.4. Многозначные термины между направлениями

Главный источник тихих промахов: слово одно, смысл разный, поиск не жалуется.

| Термин | Физика линии (спутник, РРЛ) | Стек протоколов | Типичный промах |
|---|---|---|---|
| канал | радиоканал, ствол, полоса | логический канал, соединение | «загрузка канала 80 %» → выдача про полосу ствола |
| уровень | уровень сигнала, дБм | уровень модели OSI | «просел уровень» → «канальный уровень» |
| кадр | кадр TDMA, суперкадр | кадр HDLC/Ethernet | «структура кадра» → не тот кадр |
| несущая | несущая частота, подавление несущей | несущий трафик, транспортный контейнер | «сдвиг несущей» → про транспорт |
| окно | окно прозрачности, временное окно | окно передачи, размер окна квитирования | «размер окна» → метеоусловия |
| синхронизация | символьная синхронизация, ФАПЧ | сетевая синхронизация, sync-слово | «потеря синхронизации» → чужой раздел |
| потери | потери в фидере, дБ | потери пакетов, % | «потери 3» — дБ или проценты? |
| ошибка | BER, битовая ошибка | ошибка CRC, ошибка автомата | вывод о линии по протокольной статистике |
| задержка | задержка распространения (спутник, ~250 мс) | сетевая задержка, RTT | смешение бюджета задержки |
| скорость | символьная скорость, Бод | скорость передачи, бит/с | путаница Бод и бит/с в отчёте |

### Три меры, по возрастанию цены

**1. Фильтр по направлению** — самый дешёвый и самый грубый. В коде:
`Retriever.search(..., domains=[...])` (оба поисковика поддерживают),
`GET /api/search?domains=microwave`, у разговора помощника — поле `chat.domain`,
которое `AssistantService._search` подставляет в поиск автоматически.

> Свойство, о котором надо знать: фильтр — **жёсткое отсечение**
> (`c.domain IN (...)` прямо в SQL). Документ с пустым направлением при
> включённом фильтре не находится вообще — он не «нейтрален», он невидим.
> Поэтому доля неразмеченных документов — контролируемая величина, а не
> мелочь. Смотреть `GET /api/domains`, ключ «не указано». Цель — ≤ 10 %.

Классификатор намеренно осторожен: при менее чем двух совпавших ключевых
словах и при ничьей между направлениями `classify` возвращает пустую строку.
Это правильное поведение (неверное направление хуже отсутствующего), но оно же
означает, что без ручного прохода часть библиотеки останется вне фильтров.

**2. Глоссарий с пометкой направления.** Сейчас `templates/glossary.json` —
плоское отображение «как писать нельзя → как надо», по нему считается
`glossary_compliance` (док. 05). Для многозначных терминов нужна вторая,
справочная часть — не для канонизации, а для подсказки: термин, направление,
определение, ссылка на документ. Формат:

```json
{"термин": "окно", "направление": "microwave",
 "значение": "окно прозрачности трассы", "источник": "РД …, п. 4.2"}
```

Записи, совпавшие с запросом (3–5 штук), подмешиваются в промпт помощника перед
блоком источников. Сегодня этого в коде нет — см. 13.9.

**3. Расширение запроса.** Дешёвый вариант без второй модели: к запросу
приклеиваются название направления и 2–3 его ключевых слова — они уже лежат в
`templates/domains.json`. «размер окна» + «пролёт, замирания» находит окно
прозрачности; «размер окна» + «кадр, квитирование» — окно передачи. Дорогой
вариант (попросить модель переписать запрос) окупается только на длинных
вопросах и удваивает задержку ответа.

### Как ловить промахи, а не узнавать о них от инженера

- **Набор-ловушка**: 30–40 коротких запросов ровно из таблицы выше, по два
  варианта на термин (по одному на направление), с указанием правильного
  фрагмента. Прогоняется как обычный `recall@10` (док. 05, 5.2), плюс отдельная
  метрика — **доля фрагментов чужого направления в топ-5**, цель ≤ 5 %.
- **Направление видно в выдаче**: `GET /api/search` и панель источников
  помощника возвращают `domain` каждого фрагмента. «Протоколы» в ответе на
  вопрос про пролёт — сигнал инженеру, а не украшение.
- **Журнал помощника**: в `meta` каждого ответа пишутся `found` и `cited`.
  Устойчивая доля ответов с `found > 0, cited = 0` означает, что поиск приносит
  не то — обычно из-за многозначного термина.

## 13.5. Стандарты и методички: таблицы допусков и номера пунктов

Один PDF содержит два разных по природе объекта: таблицу допусков (осмысленна
только целиком) и нумерованный текст требований (нужен адресуемо, по пунктам).

| Что | Правило индексации | Почему |
|---|---|---|
| Границы чанка | по заголовку/пункту, не по числу символов | пункт — единица цитирования |
| Пункт «5.3.2» | отдельный чанк, если он длиннее 2–3 предложений; иначе вместе с родителем 5.3 | нельзя процитировать то, что склеено с соседями |
| Таблица | целиком в одном чанке вместе с шапкой и подписью | половина таблицы допусков — это неверные допуски |
| Крошки | `Документ → Раздел → номер пункта` в `title_path` | крошки индексируются (`Chunk.indexed_text`) и попадают в ссылку (`Chunk.citation`) |
| Страница | заполнять `meta.page` при конвертации | ссылка вида «…, с. 42» |
| Приложения | таблица приложения — своим чанком | их ищут отдельно от текста |

Быстрая проверка нарезки: запрос формулировкой требования («маска передатчика,
допуск») обязан вернуть фрагмент, в ссылке которого (`Chunk.citation`) виден
номер пункта. Искать **по самому номеру** («5.3.2») сегодня бесполезно:
токенизатор режет его на «5», «3», «2» — поэтому номер обязан быть в крошках
рядом с текстом, а не служить ключом поиска (13.9). Если конвертер разваливает
большой PDF — не чините парсер героически, разрежьте исходник по главам.

### Почему номерам пунктов из памяти модели верить нельзя

Номер пункта — произвольная метка, а не смысл. Модель запомнила статистику
«в стандартах про измерения пункт обычно 5.x» и подставит правдоподобный номер,
который в вашей редакции значит другое; редакции к тому же меняются, и
нумерация уезжает. Неверная ссылка дороже неверного утверждения: утверждение
инженер оспорит на вычитке, а номер проверит, только открыв документ. Поэтому
номера в системе идут только из найденного фрагмента:

- `ASSISTANT_SYSTEM_PROMPT`, п. 1: «Числа, пороги, номера пунктов стандартов и
  значения полей бери ТОЛЬКО из источников — не по памяти».
- `SYSTEM_PROMPT`, п. 2: утверждение о норме — только со ссылкой `[S<N>]`; нет
  подходящего фрагмента — нет утверждения.
- `ASSISTANT_SYSTEM_PROMPT`, п. 2 обязывает помечать общее знание строкой
  «В библиотеке ответа нет» — граница между библиотекой и догадкой видна.
- Верификатор проверяет, что каждая ссылка указывает на реально выданный
  фрагмент; `citation_precision` в эвале считает долю таких ссылок.

### Как добиться цитаты, а не пересказа

1. Пункт целиком должен помещаться в чанк: модель не процитирует то, чего ей не
   показали.
2. В `instruction` секции шаблона писать прямо: «приведи дословную формулировку
   требования в кавычках со ссылкой», а не «опиши требования».
3. Ограничивать `retrieval_doc_types` у секций про нормы: в
   `templates/outline_signal_issue.json` секции «условия» и «методика» уже
   сужены до `["literature", "standards"]`, а для секции с прямой ссылкой на
   норму оставляйте только `["standards"]`. Иначе в контекст попадёт пересказ
   нормы из чужого отчёта — и модель перескажет пересказ.
4. Выборочная проверка: 20 утверждений «согласно…» в месяц открываются по
   ссылке и сверяются дословно. Это та же выборка, что нужна для
   `citation_precision` (док. 05, 5.2), отдельной работы не добавляется.

### Числа из таблиц допусков — отдельный случай

Фраза «измеренное значение 12,3 % при допуске не более 10 %» содержит два
числа: первое из факт-пакета, второе — из стандарта. Верификатор о втором
ничего не знает и заблокирует отчёт (док. 01, инвариант 1). Правильный способ —
завести норму **отдельным измерением** факт-пакета с ссылкой на пункт:

```json
"evm_limit": {"title": "Допуск на EVM", "value": 10, "unit": "%",
              "source": "ГОСТ …, п. 5.3.2"}
```

Добавить поле `limit` внутрь существующего измерения нельзя:
`Measurement.from_dict` отвергает неизвестные поля. Норма, попавшая в
факт-пакет, автоматически попадает в множество разрешённых чисел
(`FactPack.allowed_numbers`), и отчёт проходит проверку.

## 13.6. Обучающие данные по направлениям

### Что происходит с вашими 200 и 40

Расчёт по правилам док. 03 (отбор оценки 4–5, дедупликация, 6–10 секций на
отчёт):

| Направление | Отчётов | Оценка 4–5 (~60 %) | После дедупликации | Пар секций | Решение |
|---|---|---|---|---|---|
| Спутник | 200 | ~120 | ~100 | ~700 | ограничить сверху до ~400 |
| Релейка | 40 | ~24 | ~20 | ~140 | взять все, не дублировать |
| Протоколы | 60 | ~36 | ~30 | ~210 | взять все |
| Прочее | 30 | ~18 | ~15 | ~100 | взять все |
| **Итого** | 330 | ~198 | ~165 | **~850** | один набор, один адаптер |

850 пар — это рабочий объём для LoRA (док. 03, 3.6: 300–800 уже дают сдвиг,
2000+ заметно лучше). Разбитые на четыре набора те же данные не дают ничего.

### Правила

1. **Один адаптер, один набор.** Отдельный адаптер на 140 парах — это не
   специализация, а заучивание двадцати отчётов.
2. **Балансировать ограничением сверху, а не дублированием снизу.** Обрезать
   частое направление до 2–3 медиан по набору. Дублирование редкого направления
   ×5 эквивалентно пяти эпохам по нему — то же переобучение, но незаметное.
3. **Отбирать в частом направлении разнообразие, а не свежесть**: сначала по
   одному представителю из каждой группы дедупликации, потом добирать по оценке.
4. **Не выкидывать редкое направление совсем.** 140 пар не научат «стилю
   релейного отчёта», но удерживают лексику и структуру в пределах нормы.
5. **Негативные примеры** («данных недостаточно», док. 03, 3.5) распределять по
   направлениям пропорционально, а не набирать все из спутника — иначе модель
   научится осторожничать только там.
6. **Эпох 2, а не 3**, если перекос между направлениями больше 3:1.

### Симптомы переобучения на частом направлении

| Симптом | Чем ловится |
|---|---|
| В отчёте по релейке появляются спутниковые обороты («наклонная дальность», «дождевое затухание») без фактов | экспертная вычитка; автометрики это пропускают |
| `reference_similarity` вырос на спутнике и упал на релейке | разбивка эвала по направлениям |
| Доля `[ТРЕБУЕТ ПРОВЕРКИ]` резко упала | модель перестала признавать нехватку данных — регресс, а не прогресс |
| Одинаковые вводные абзацы во всех отчётах | дедупликация обучающего набора была недостаточной |

### Эвал с разбивкой по направлениям

- В золотом наборе — **не менее 5 кейсов на каждое направление, где вообще
  есть отчёты**. При целевом размере 40–60 кейсов (док. 05, 5.1) это выполнимо.
- В манифест золотого набора добавить кейсам поле `"domain": "microwave"`.
  Менять код не нужно: `load_golden_set` переносит все дополнительные поля
  кейса как есть.
- `reportgen eval --golden … --out var/eval/run.md` кладёт рядом
  `run.json` с метриками по каждому кейсу (`case_id` + метрики). Разбивка —
  группировка этого JSON по `domain` из манифеста. Своего отчёта по
  направлениям харнесс пока не строит (13.9).
- **Правило приёмки: смотреть худшее направление, а не среднее.** Средний
  `citation_precision` 0.91 при 0.62 по релейке — это провал по релейке.

## 13.7. Первые три месяца: только разбор библиотеки

Этот план — детализация этапа 2 дорожной карты (док. 06) в части данных. Он не
требует ни дообучения, ни смены модели.

### Месяц 1 — инвентаризация и приём

| Работа | Результат |
|---|---|
| Пройти таблицу 3.1 док. 03, добавив колонку «направление» | список источников с объёмами, правами и направлениями |
| Разложить файлы по `library/<тип>/…` | тип документа задан каталогом, а не мнением |
| Разрезать подшивки и комплекты на отдельные документы | один файл — один документ |
| `reportgen ingest` и разбор предупреждений | все документы в базе |

**Критерии выхода:** `failed = 0` в сводке приёма; каждый документ имеет тип,
заданный каталогом; ни одного файла крупнее 300 страниц, оставшегося одним
документом; доля документов без направления ≤ 25 %.

### Месяц 2 — разметка, классификатор, глоссарий

| Работа | Результат |
|---|---|
| Руками проставить направление всем стандартам и топ-100 документов по объёму | `PUT /api/library/{doc_id}/domain`; переиндексация не требуется |
| Проверить классификатор на 100 размеченных вручную документах | точность и полнота по каждому направлению |
| Поправить ключевые слова в `templates/domains.json` по результатам | файл перечитывается автоматически |
| Собрать глоссарий: 80–150 терминов с пометкой направления | все многозначные термины из 13.4 внутри |

**Критерии выхода:** доля документов без направления ≤ 10 %; точность
классификатора ≥ 0.85 на контрольной сотне; доля «уверенно, но неверно» ≤ 5 %
(пустой ответ ошибкой не считается — он безопасен); 100 % стандартов размечены
человеком; глоссарий покрывает все термины из таблицы 13.4.

### Месяц 3 — измерение поиска

| Работа | Результат |
|---|---|
| 200–300 пар «запрос → нужный фрагмент», пропорционально объёму, но ≥ 25 пар на направление | эвал поиска (док. 05, 5.2) |
| Набор-ловушка на многозначные термины (30–40 запросов) | метрика чужого направления в топ-5 |
| Прогон `recall@10` **по каждому направлению отдельно** | таблица по направлениям, а не одно число |
| 20 контрольных вопросов «что говорит пункт …» | проверка цитирования |

**Критерии выхода:** `recall@10` ≥ 0.85 **в каждом** направлении, где набрано
≥ 25 пар (док. 06, этап 2 требует этого в среднем — здесь требование строже);
доля чужого направления в топ-5 на наборе-ловушке ≤ 5 %; 20 из 20 контрольных
вопросов дают дословную цитату пункта с работающей ссылкой.

### Чего в эти три месяца не делать

Не дообучать, не менять базовую модель, не заводить восьмое направление. Пока
`recall@10` ниже 0.85, любое улучшение генерации измеряется шумом поиска: вы
будете править промпты в ответ на промахи RAG.

## 13.8. Как добавить новое направление (пример: тропосферная связь)

| Шаг | Что сделать | Кто | Время |
|---|---|---|---|
| 1 | Строка в `templates/domains.json`: `{"id": "troposcatter", "title": "Тропосферная связь", "keywords": [...]}` — 10–20 характерных слов («тропосферн», «загоризонтн», «рассеяни», «разнесённый приём», «медианные потери», «угол рассеяния»). Файл перечитывается по mtime, перезапуск не нужен | инженер | 30 мин |
| 2 | Загрузить документы, **указывая направление явно** (`domain=troposcatter` в форме загрузки) — не полагаться на классификатор, пока ключевые слова не откалиброваны | инженер | по мере поступления |
| 3 | Если структура отчёта отличается — `templates/outline_troposcatter.json` по образцу; если нет — использовать существующий шаблон | старший инженер | 1–2 дня |
| 4 | Добавить термины в глоссарий, пометить пересекающиеся с РРЛ («разнесение», «замирания») | инженер | 2 часа |
| 5 | 15–25 пар «запрос → фрагмент» и 3–5 кейсов в золотой набор с `"domain": "troposcatter"` | инженер | 1 день |
| 6 | Прогнать `classify` по уже размеченным документам РРЛ и убедиться, что новые ключевые слова не утащили их в ничью | разработчик | 1 час |

Шаг 6 — единственный настоящий риск: пересекающиеся ключевые слова дают
равенство очков, а при ничьей `classify` возвращает пустую строку, и документ
выпадает из фильтра по своему прежнему направлению. Проверяется одним прогоном
по базе до и после правки `domains.json`.

### Чего делать НЕ нужно

| Не нужно | Почему |
|---|---|
| Переобучать модель | направление — это факты, факты приходит RAG (док. 01, 1.3) |
| Заводить отдельный адаптер | нет 300 отчётов, а стиль тот же самый |
| Менять код | направления — данные в `templates/domains.json`, тип — каталог |
| Перестраивать каталоги библиотеки | направление — поле документа, а не путь |
| Перестраивать векторы | смена направления не меняет текст чанка; `reportgen embed` нужен только для новых документов |
| Заводить новый тип документа | тропосферный ГОСТ — это `standards`, как любой другой |
| Ждать «полноты» библиотеки перед запуском | направление работает с первого документа, просто с низким recall |
